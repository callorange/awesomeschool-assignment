# 기능 검증 가이드

과제 검토자가 [README의 로컬 실행](../../README.md#로컬-실행)을 마친 뒤 기능과 한계를 확인하는 안내입니다. 개발 규칙은 [개발 규약](../development.md)에서 별도로 관리합니다. 명령은 저장소 루트에서 Bash로 실행합니다.

## 화면과 접수 확인

| 확인 순서 | 예상 결과 |
| --- | --- |
| 랜딩 → 교육 상세 | 프롬프트·감정탐험·관계 히어로 3개와 목표·대상·커리큘럼·진행 안내가 보입니다. |
| 상세 → 상담 신청 | 교육정보 API를 읽어 선택 교육·접수 가능 여부를 표시합니다. |
| 주소 검색·취소·직접 입력 | 우편번호·기본주소를 채우고 상세주소로 이동합니다. 취소·SDK 장애에도 기존 입력을 보존합니다. |
| 유효한 신청 제출 | 이름·이메일·우편번호·기본주소·연락 가능 날짜를 검증하고 `접수`·식별자를 표시합니다. 상세주소는 선택입니다. |
| 오류·전송 중 상태 | 필드 오류를 표시하고 첫 오류로 이동하며 전송 중 편집·중복 클릭을 막습니다. |
| 신청 관리 | `/backoffice/`에서 신청·상담·재연락·메일 상태를 확인하고 `/admin/`에서 이력 상세·기존 관리 기능을 확인합니다. 신청·상담은 삭제하지 않습니다. |

Kakao 공식 SDK는 주소 검색 버튼을 누를 때 외부 HTTPS로 로딩합니다. 연결이 안 되면 직접 입력으로 접수할 수 있습니다. 검색 요청에 신청자 이름·이메일·상세주소를 추가하지 않습니다. Axios·CSS는 로컬 자산입니다.

## 자동 안내 확인

1. README의 `configure_background_tasks`를 실행하고 별도 터미널에서 `qcluster`를 유지합니다.
2. 오늘 날짜로 신청합니다. 한국 시각 09시 이후 신청은 다음 검사 대상이며, 이전이면 09시까지 기다립니다. 미래 날짜는 그 날짜 09시부터 대상입니다.
3. `notification_status`에서 안내 상태가 `pending` → `queued` → `sending` → `simulated`로 처리되는지 확인합니다. 중간 상태는 짧아 조회에서 보이지 않을 수 있습니다.

```bash
uv run python src/manage.py notification_status
```

검사 간격은 5분이고 큐 대기로 더 늦어질 수 있습니다. locmem 메일 본문은 worker 메모리에만 존재하며 console·실제 수신함에는 출력·전달되지 않습니다. 처리 여부는 DB의 상태·`simulated_at`으로 확인하며 `sent_at`·SES MessageId는 비어 있습니다.

시각을 기다리지 않고 로직을 검증하려면 테스트 DB에서 실행하는 다음 검사를 사용합니다. 날짜 경계·모의 전송·한 번 처리·선별 재시도·unknown 보존을 확인하며 실제 신청 기록을 수정하지 않습니다.

```bash
uv run python src/manage.py test education.tests.test_api education.tests.test_notifications
```

선택적으로 superuser를 만든 뒤 `/admin/`의 Q2 스케줄·성공/실패 작업을 확인할 수 있습니다. 스케줄은 admin에서 수정하거나 `repeats=0`으로 중지할 수 있습니다. 준비 명령 재실행은 5분 간격·무제한 반복·default cluster를 다시 적용하지만 기존 다음 실행 시각은 유지합니다. 이미 큐에 들어간 작업은 스케줄 수정·중지로 취소되지 않습니다.

```bash
uv run python src/manage.py createsuperuser
```

## API 계약

과제의 GET은 **신청 화면에서 사용할 교육정보 조회**로 해석했습니다. 신청자 개인정보를 공개하는 GET은 제공하지 않습니다.

| Method·경로 | 역할 |
| --- | --- |
| `GET /api/educations/<slug>/` | slug·title·summary·image_url·image_alt·operation_type·operation_note·is_accepting_inquiries 반환 |
| `POST /api/applications/` | JSON 입력 검증, 신청·안내 대상 원자적 생성, 접수 결과 반환 |
| `GET /api/applications/` | 405. 공개 신청 목록 없음 |

교육정보는 다음처럼 확인할 수 있습니다.

```bash
curl -i http://127.0.0.1:8000/api/educations/prompt-hero/
```

신청 POST는 신청 화면이 받은 CSRF cookie와 `X-CSRFToken` header가 필요합니다. 브라우저에서 폼을 제출한 뒤 개발자 도구의 Network에서 요청·응답을 확인하는 것이 기본 검토 경로입니다.

| JSON 입력 | 계약 |
| --- | --- |
| `education_slug` | 선택한 교육의 slug |
| `name`·`email` | 필수, 각각 최대 100자·254자, 이메일 형식 검사 |
| `postal_code`·`address` | 필수, 숫자 5자리 우편번호·최대 255자 기본주소 |
| `address_detail` | 선택, 최대 255자, 생략하면 빈 문자열 |
| `contact_date` | `YYYY-MM-DD`, 한국 날짜 기준 오늘 포함 이후 |
| `request_id` | 클라이언트가 생성하는 UUID, 같은 제출의 재시도에서 유지 |

최초 생성은 201, 같은 식별자·정규화 입력의 재요청은 200입니다. 두 경우 모두 응답 필드는 `request_id`·`status=received`·`status_display=접수`뿐이며 내부 PK·개인정보는 반환하지 않습니다.

| 오류 | 결과 |
| --- | --- |
| 필드 오류·미정의 쓰기 필드·신규 접수 중단 | 400, DRF 필드별 문자열 배열 또는 non_field_errors |
| 없는 교육 | 404, detail |
| 익명 요청을 포함한 CSRF 누락·실패 | 403, HTML 응답일 수 있음 |
| 같은 request_id에 다른 입력 | 409, detail. 새 ID로 자동 재전송하지 않음 |

문자열의 바깥 공백은 제거하되 이메일 대소문자·주소 내용은 자의적으로 변경하지 않습니다. 기존 제출 확인은 신규 접수 조건과 구분하므로 접수 후 날짜 경과·교육 중단·slug 변경·삭제가 있어도 원래 입력·ID로 기존 결과를 확인합니다. 교육 삭제 후 신청은 보존하고 안내에는 신청 당시 교육명·slug snapshot을 사용합니다.

## 응답 유실·주소 검색 장애 재현

고급 수동 검증용 HTTP fixture입니다. 별도 개발 DB에서 사용하며 **폼 제출은 실제 개발 DB에 테스트 신청을 저장**합니다. 실제 API·ORM 경로는 유지하고 응답 경계와 외부 주소 SDK만 대체합니다. 운영 URL에 등록하지 않습니다.

두 터미널을 저장소 루트에서 실행합니다.

```bash
# 터미널 1: 실제 Django 서버
uv run python src/manage.py runserver 127.0.0.1:8001 --noreload
```

```bash
# 터미널 2: loopback 전용 검증 proxy
uv run python src/education/tests/ui_proxy.py
```

브라우저에서 `http://127.0.0.1:8002/educations/prompt-hero/apply/?case=lost-csrf`를 열고 테스트 정보로 제출합니다. 여러 시나리오는 순차 검증하며 같은 시나리오를 처음부터 반복할 때는 proxy를 재시작합니다. `--noreload` 서버는 Python 변경 후 직접 재시작합니다.

| case | 재현·확인 내용 |
| --- | --- |
| `normal` | fixture 주소 선택 후 실제 신청 저장·접수 표시 |
| `lost` | 실제 최초 저장 후 실패 응답. 입력을 잠그고 같은 ID로 재확인해 200 반환 |
| `lost-csrf` | 저장 후 응답 유실 → 재시도 403 → CSRF 갱신 → 같은 ID 재확인 |
| `invalid` | 첫 제출의 필드 오류·오류 focus·입력 수정 후 재제출 |
| `conflict` | 409에서 새 ID 자동 생성·전송 없이 중단 |
| `get-failure`·`stopped` | 교육 조회 실패·중단 상태에서 신규 제출 비활성화 |
| `sdk-error` | 주소 SDK 실패 후 기존 입력 유지·직접 입력 |
| `official` | fixture SDK 대신 실제 Kakao 주소 검색. 외부 연결 필요 |

브라우저의 결과 미확인 요청은 메모리의 원래 payload·ID로만 재시도합니다. 개인정보를 localStorage에 남기지 않으므로 새로고침·탭 종료 후 이전 제출 복구는 지원하지 않습니다. 별도의 새 ID로 만든 신청까지 이메일 주소만으로 차단하지는 않습니다.

## 자동 테스트와 정적 검사

로컬 PostgreSQL은 기본 `test_awesomeschool` DB를 생성·삭제합니다. `POSTGRES_DB`를 바꾸면 테스트 DB 이름도 바뀝니다. 공유·운영 DB 설정으로 실행하지 않습니다. 미디어는 임시 디렉터리에 격리합니다.

```bash
uv run python src/manage.py check
uv run python src/manage.py makemigrations --check --dry-run
uv run python src/manage.py test education
uv run ruff check .
uv run ruff format --check .
```

화면·DB·상태 전이·transaction은 실제 경로로 확인합니다. SES는 실제 django-ses backend를 사용하되 외부 SDK만 fake하고 개발 메일은 실제 locmem으로 검사합니다. qcluster subprocess는 테스트 DB·미디어에서 결과 저장·강제 종료 복구·이미지 실패 후 재등록을 확인합니다.

## 검증 기록과 한계

최신 전체 자동 테스트는 2026-10-23 Windows의 154개 통과 결과입니다. 화면·배포 자산·장애 재현의 검증 시점과 상세 범위는 아래 백오피스·신청 프리셋별 실행 기록을 따릅니다. 문서를 Bash 기준으로 작성한 것과 macOS/Linux에서 실제 검증한 것은 구분합니다.

| 항목 | 확인 범위 |
| --- | --- |
| 자동 테스트 | 154개 통과. 기존 백오피스 17개·관리자 권한·신청/상담 보존·이력·동시 제출·claim·공유 예산·재시도·이미지 보호와 신청 프리셋 11개·백오피스 프리셋 통합 2개를 포함합니다. [최신 실행 결과](#신청-프리셋-구현-검증-결과) |
| qcluster | 실제 subprocess 4개 테스트: 기존 공개 task 경로·후속 검사·run-once 정상 종료/결과 저장·강제 종료 복구·이미지 실패 재등록 |
| 실제 브라우저 | 교육 GET → 주소 검색/입력 → 신청 POST → 접수 표시, 응답 유실·CSRF·400·409·SDK 장애. 백오피스·신청 샘플 32건의 20/12건 페이지네이션·검색·상담·8종 모의 이메일 상태·입력 보존 |
| 반응형 | desktop 브라우저 360/390/768/1280px에서 넘침 없음·48px 입력 높이·오류/주소 focus |
| 배포 자산 | 공개 신청 화면 자산은 lockfile·캐시 기반 재설치 후 `npm run build`로 생성한 CSS·JS·source map·라이선스 4개 hash 일치·HTTP 200을 확인했습니다. 교육 admin JS는 추가 후 빌드·HTTP 200·실제 교시 추가 동작을 확인했습니다. 외부 JS import 없는 번들·Axios 라이선스 원문 보존 확인 |
| JS 번들 실행 | 브라우저에서 교육 GET·주소 SDK fixture·Axios POST의 400 필드 오류와 이메일 포커스 확인 |
| 진입점·페이지별 로딩 | 임시 진입점 자동 탐색·Axios 공통 chunk 분리·생성 모듈 실행 확인. Django 페이지 테스트 10개 통과: 신청 페이지만 신청 JS를 한 번 로드. 교육 admin은 커리큘럼 위젯의 Media로 별도 JS 로드 |

SES 접수 여부가 불명확한 `unknown`은 자동 해소하지 못합니다. 중복 방지를 위해 자동 재발송하지 않으므로 실제 미발송일 가능성도 남습니다. 신청·상담은 보존하며 백오피스와 기본 admin으로 관리합니다. Spreadsheet 내보내기·SNS/웹훅·실제 전달/반송 추적은 미구현입니다.

## 백오피스 확인

1. README 절차로 계정을 만든 뒤 `/backoffice/login/`에 로그인합니다. 같은 계정으로 `/admin/`에도 접근하고 한쪽에서 로그아웃하면 두 화면 모두 재로그인이 필요한지 확인합니다. 비로그인 GET은 로그인으로 이동하고 일반 사용자·비활성 계정·신청 조회 권한 없는 staff는 업무 화면을 조회할 수 없습니다.
2. 목록에서 이름·이메일 검색과 교육명·상태·재연락 필터를 적용합니다. 교육명은 신청 당시 snapshot이므로 원본 교육이 없어도 찾을 수 있습니다. 최신순 페이지당 20건이며 페이지를 이동해도 조건이 URL에 유지됩니다. 오늘 재연락·기한 경과는 한국 시각 기준이며 서로 겹칠 수 있습니다.
3. 신청 상세에서 개인정보·연락 가능 날짜·상태·재연락 일정을 정정합니다. 신청 변경 권한만 있으면 **변경사항 저장**, 상담 추가 권한만 있으면 읽기 전용 신청과 **상담 추가**가 표시됩니다. 둘 다 있으면 기본 해제된 **상담 기록도 추가**를 선택하여 신청과 상담을 한 번에 저장합니다. 선택하지 않은 상담 필드는 저장하지 않습니다.
4. 상담 추가를 선택하거나 상담 전용으로 저장할 때 결과·내용은 필수입니다. 잘못된 상담이 있으면 신청 정정도 저장하지 않으며 선택 상태와 입력을 유지합니다. 기존 기록 수정·삭제는 제공하지 않습니다. 정정은 상담 조회·추가 권한이 있을 때 같은 신청의 원기록을 선택해 새 기록으로 남깁니다. 작성자·시각·당시 변경 후 일정은 서버 값입니다.
5. 이름·이메일·연락 날짜 변경과 완료·취소는 안내 발송 중에 거부합니다. 취소 사유·새 과거 일정·우편번호·이메일 오류를 확인하고 기존 입력이 유지되는지 확인합니다. 저장 후 새로고침은 상담을 다시 추가하지 않습니다. 변경 이력 상세는 Django admin에서 확인합니다.
6. 메일 조회 권한을 가진 담당자의 상세에서 **상태 새로고침**을 누릅니다. 이메일 영역만 Ajax GET으로 교체되고 작성 중인 신청·상담과 버튼 focus는 유지됩니다. `모의 완료`, `SES 접수`, `실패`, `결과 확인 필요`, `발송 중단`을 구분하며 SES 접수는 수신함 도착이 아닙니다. 자동 polling·재발송·task 제어는 없습니다.
7. 부분 갱신 실패는 기존 표시와 입력을 유지하며 최신 조회 실패를 알립니다. 세션 만료는 재로그인 필요와 별도 탭 로그인 링크, 권한 거부는 접근 거부를 표시합니다. 자동으로 페이지를 이동하거나 제출하지 않습니다. JavaScript가 없으면 부분 갱신을 사용할 수 없지만 최초 이메일 상태·일반 폼 저장·native 상담 선택은 사용할 수 있습니다.

## 기존 Django admin 검증 기록

백오피스 추가 전인 2026-10-22 Windows에서 당시 전체 education 테스트 124개를 통과했습니다. 이후 백오피스를 포함한 141개 결과는 [백오피스 구현 검증 결과](#백오피스-구현-검증-결과), 최신 전체 154개 결과는 [신청 프리셋 구현 검증 결과](#신청-프리셋-구현-검증-결과)를 따릅니다. 2026-10-22 사용자 요청으로 Compose의 로컬 `awesomeschool` DB를 재생성한 뒤 교육 프리셋 3개·안내 검사 스케줄 1개·프로젝트 초기 migration 1개를 확인했습니다. 신청·안내 이메일·계정은 0건이며 프리셋 값이 원본과 일치함을 확인했습니다. 미디어와 다른 DB는 삭제하지 않았습니다. 이후 docstring·주석 보완에서는 전체 테스트를 반복하지 않고 Python 47개 파일의 docstring 제외 AST와 admin JS 실행 번들 hash가 동일함을 확인했으며 lint·format·JS 빌드·공백 검사를 통과했습니다. 이 기록은 당시 실행 결과이며 이후 개발 DB의 현재 데이터 건수를 보장하지 않습니다.

## 신청 샘플 확인

[개발용 신청 샘플 준비](operations.md#개발용-신청-샘플) 후 worker를 시작하기 전에 확인합니다. 일반 신청이 있으면 이름·이메일 검색에 `application-preset-`를 입력합니다.

1. 최신순 첫 페이지 20건·다음 페이지 12건에서 세 교육과 다섯 신청 상태가 섞이는지 확인합니다. 이메일 번호가 01부터 32까지 최신순이며 교육·상태·재연락 검색 조건을 변경하고 페이지 링크의 조건 보존도 확인합니다.
2. 01번은 상담 없음, 02번은 원문과 정정, 03번은 부재중과 재연락 합의입니다. 완료·취소 번호에서 현재 일정 비움과 취소 사유를 확인합니다. 상담 시각은 접수 이후이고 다음 연락 예정과 연락 가능 날짜는 별도 값입니다.
3. 이메일은 01 pending·02 queued·19 sending·03 simulated·18 retry_wait·17 failed·05 unknown·09 suppressed를 대표로 확인합니다. 합성 상태를 실제 발송으로 해석하지 않으며 SES 접수 증거는 없습니다. 상세의 상태 새로고침이 작성 중 입력을 보존하는지 확인합니다.
4. 이름/이메일·주소·상태·일정을 정정하고 상담을 추가한 뒤 명령을 재실행해 수정값과 상담·이력이 유지되는지 확인합니다. 샘플을 원래대로 돌리기 위해 개발 DB를 삭제하지 않습니다.
5. 초기 화면 확인 후 필요한 경우 개발 worker를 시작합니다. 대기·재시도와 만료 큐·발송 중 상태의 변화는 기존 처리·복구 정책을 따릅니다. 날짜가 지나면 오늘·기한 경과 건수도 달라지므로 최초 분포와 구분합니다.

화면 검증은 기존 개발 DB에 샘플을 넣는 대신 별도 PostgreSQL 테스트 DB·임시 미디어·가상 staff에서 수행합니다. 기존 141개 테스트 통과 기록은 이전 백오피스 기준선이며 신청 프리셋을 포함한 최신 결과는 [아래 실행 기록](#신청-프리셋-구현-검증-결과)에서 확인합니다.

### 신청 프리셋 구현 검증 결과

2026-10-23 Windows에서 전체 education 테스트 **154개**를 통과했습니다. 신청 프리셋 11개와 백오피스 프리셋 통합 2개가 기존 141개에 추가됐습니다. 먼저 프리셋·공개 페이지·백오피스 범위 45개를 통과했고, 기존 worker의 샘플 복구·처리를 검사하는 1개를 추가한 뒤 전체 154개를 확인했습니다. Django check·migration 누락 검사·Ruff lint/format·diff 공백 검사도 통과했습니다. python-dateutil 2.9.0.post0은 버전 변경 없이 공통 직접 의존성으로 명시했고 uv lock은 offline 캐시로 동기화했습니다.

실제 PostgreSQL 테스트 DB와 임시 미디어에서 32건·교육 11/11/10·상태 8/6/10/4/4, 날짜·상담 정정·history·메일 시도 연결과 한국/UTC 날짜 차이를 검증했습니다. 담당자 정정과 상담 추가·교육 연결 해제 후 다른 날 재실행해 전체 snapshot을 비교했고, 일부 존재·고정 식별자 충돌·환경/담당자 오류·상담/안내/시도/history 저장 실패의 rollback도 확인했습니다. 메일 발송과 큐 경계 호출 없음, 기존 큐·스케줄·예산·계정의 불변, 반환 이미지 키 변경 시 정리 큐 없음도 확인했습니다. 기존 task의 만료 queued/sending 복구와 도래 대상의 locmem 처리·미도래 대상 대기·종료 기록 보존은 실제 ORM 경로로 검증했으며 AWS 호출은 없었습니다.

별도 무작위 이름 PostgreSQL 테스트 DB와 임시 미디어에 준비한 32건으로 loopback 서버를 실행했습니다. 실제 앱 내 브라우저에서 가상 staff 로그인, 첫 페이지 20/두 번째 12건, 교육·상태 혼합 목록, 이메일 접두어 검색·조건 보존 링크·오늘 재연락 3건, 상담 없음·복수·정정·취소 사유·8종 메일 상태를 확인했습니다. 상세의 이메일 상태 새로고침은 작성 중인 이름 입력을 유지했습니다. 목록과 상세를 각각 360/390/768/1280px에서 측정했으며 document scrollWidth는 345/375/753/1265px로 가로 넘침이 없었습니다. CSS와 상세 JavaScript·이메일 partial의 HTTP 응답도 정상 확인했습니다. 확인 후 브라우저 viewport를 복구하고 검증 서버·테스트 DB·임시 미디어를 정리했습니다. 기존 개발 DB·미디어에는 샘플을 생성하지 않았습니다.

sandbox 내부의 첫 프리셋 테스트는 임시 디렉터리 접근 WinError 5로 실패해 필요한 명령 단위 권한으로 재실행했습니다. uv 기본 캐시 접근도 sandbox에서 실패했고 프로젝트 안의 빈 캐시는 offline 의존성 해석에 필요한 패키지를 갖고 있지 않아, 기존 사용자 캐시에 명령 단위 권한으로 접근해 잠금 버전을 보존했습니다. 이후 검사는 프로젝트 .venv 실행 파일을 사용했습니다. Django override_settings가 SETTINGS_MODULE을 초기화하는 테스트 특성은 fixture에 개발 설정 식별자를 명시해 처리했으며 실제 실행 환경 제한을 완화하지 않았습니다.

macOS/Linux 전체 실행·Android Chrome/iOS Safari 실기기·AWS 실발송·실제 SES 접수는 이번에도 미검증입니다. 화면용 합성 상태는 실제 상담·전송 증거가 아니며 worker를 켜거나 날짜가 지나면 최초 분포가 변할 수 있습니다. 변경 범위의 환경 제한·일반 save/history·보존/rollback과 문서를 django-reviewer 관점으로 대조했고 현재 범위의 blocking defect는 발견하지 않았습니다.
