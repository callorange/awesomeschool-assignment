# Spec Delta

## Purpose

관리자가 신청 내역을 삭제하지 않고 상담 진행과 재연락 일정을 관리하게 한다. 신청 정보의 변경 근거와 상담 경과를 보존하고, 권한이 있는 사용자만 개인정보와 내부 안내 현황을 조회하게 한다.

## ADDED Requirements

### Requirement: 관리자 접근과 작업 권한

시스템은 기본 관리자 화면에서 로그인한 활성 관리자에게 부여된 모델별 조회·변경·기록 추가 권한을 적용해야 한다(SHALL). 관리자 여부만으로 모든 신청·상담·이력을 공개하지 않아야 한다(SHALL). 신청 수동 생성 화면과 사용자 직접 취소 기능은 제공하지 않아야 한다(SHALL).

#### Scenario: 비로그인과 권한 없는 사용자
- **WHEN** 비로그인·일반 사용자 또는 해당 조회 권한이 없는 관리자가 신청·상담·이력 화면에 접근한다
- **THEN** 로그인 또는 접근 거부로 처리하고 개인정보를 노출하지 않는다

#### Scenario: 조회만 허용된 관리자
- **WHEN** 조회 권한만 가진 관리자가 신청을 조회한 뒤 직접 POST로 변경을 시도한다
- **THEN** 조회는 허용하지만 변경과 상담 기록 추가는 해당 권한 없이는 거부한다

### Requirement: 신청 목록과 상세 조회

시스템은 신청 당시 교육명·이름·이메일·연락 가능 날짜·현재 상태·다음 연락 예정·신청 일시가 포함된 페이지 단위 목록과 상세를 제공해야 한다(SHALL). 이름·이메일 검색과 교육·상태·연락 가능 날짜 필터를 제공하고 교육 원본이 없어도 신청 당시 교육 정보를 표시해야 한다(SHALL).

#### Scenario: 검색과 교육 삭제 이후 조회
- **WHEN** 관리자가 이름·이메일로 검색하거나 교육·상태·날짜로 필터링한다
- **THEN** 조건에 맞는 신청을 조회하며 원본 교육이 삭제된 신청도 당시 교육명과 입력 내용을 확인할 수 있다

### Requirement: 신청 정보 정정과 데이터 보존

시스템은 이름·이메일·우편번호·기본주소·상세주소·연락 가능 날짜의 정정을 허용하고 필수값·길이·이메일·우편번호 형식을 검증해야 한다(SHALL). 최초 제출 식별자·원본 입력·신청 당시 교육 정보·신청 일시는 관리자가 바꿀 수 없어야 한다(SHALL). 신청과 상담 기록의 개별·일괄 삭제를 제공하지 않아야 한다(SHALL).

#### Scenario: 과거 신청 정정
- **WHEN** 연락 가능 날짜가 이미 지난 신청의 이름이나 주소를 정정한다
- **THEN** 과거 날짜가 유지됐다는 이유로 거부하지 않고 유효한 정정만 저장하며 원본 입력은 보존한다

#### Scenario: 날짜 정정과 삭제 우회 시도
- **WHEN** 연락 가능 날짜를 새 과거 날짜로 바꾸거나 삭제 URL·일괄 삭제 요청으로 신청을 제거하려 한다
- **THEN** 새 과거 날짜와 삭제는 거부하며 신청·상담·안내 기록을 보존한다

### Requirement: 상담 진행 상태와 종료 사유

시스템은 접수·상담중·재연락 예정·완료·취소를 구분해야 한다(SHALL). 신규 신청은 접수이고 상태는 관리자가 변경해야 한다(SHALL). 취소는 상담 후 진행하지 않기로 확정한 결과로 처리하며 사유를 기록해야 한다(SHALL). 메일 처리와 부재중 횟수만으로 상태를 자동 변경하지 않아야 한다(SHALL).

#### Scenario: 상담 이후 취소
- **WHEN** 상담자가 진행하지 않기로 확정해 취소 상태를 저장한다
- **THEN** 취소 사유가 없으면 저장을 거부하고 사유가 있으면 신청과 상담·변경 기록을 보존한다

#### Scenario: 완료 또는 취소 후 목록 조회
- **WHEN** 완료·취소 상태로 종료한 신청을 조회한다
- **THEN** 상태 필터로 다시 조회할 수 있으며 데이터가 삭제되거나 별도 보관 기능으로 숨겨지지 않는다

### Requirement: 재연락 일정과 대상 조회

시스템은 신청자의 연락 가능 날짜와 별개로 다음 연락 예정 일시를 한국 시각으로 관리해야 한다(SHALL). 재연락 예정에서 일정 미정을 허용하고 오늘 예정·기한 경과·일정 미정을 구분해 조회해야 한다(SHALL). 다른 상태에서는 현재 다음 연락 예정을 비우되 지난 일정 기록은 보존해야 한다(SHALL).

#### Scenario: 일정 변경과 미정
- **WHEN** 재연락 예정 신청의 일정을 변경하거나 미정으로 둔다
- **THEN** 최초 연락 가능 날짜를 변경하지 않고 이전 일정은 기록에 남기며 재연락 목록에서 새 일정 또는 미정을 구분한다

#### Scenario: 재연락 일정 입력 오류와 종료
- **WHEN** 새로 정하는 다음 연락 예정이 과거이거나 완료·취소로 상태를 바꾼다
- **THEN** 새 과거 일정은 거부하고 종료 시 현재 일정은 비우되 과거 기록은 유지하며 기존 기한 경과 일정만 유지하는 다른 정정은 허용한다

### Requirement: 상담 기록의 누적과 정정

시스템은 신청별 작성자·작성 시각·연락 결과·내용·당시 다음 연락 예정 일시를 누적해야 한다(SHALL). 연락 결과는 상담 진행·부재중·재연락 합의·정정으로 구분하고 내용은 필수여야 한다(SHALL). 기존 기록의 수정·삭제를 금지하며 정정은 대상 원기록을 식별하는 새 기록으로 남겨야 한다(SHALL).

#### Scenario: 부재중 이후 재연락 합의
- **WHEN** 부재중 기록 이후 통화해 재연락 일정을 합의한다
- **THEN** 두 기록의 작성자·시각·내용·당시 일정을 각각 확인하며 이전 기록이 덮어써지지 않는다

#### Scenario: 잘못 작성한 내용 정정
- **WHEN** 관리자가 기존 기록을 정정한다
- **THEN** 같은 신청의 원기록에 연결된 새 정정 기록을 추가하고 원문은 남으며 다른 신청의 기록을 정정 대상으로 지정할 수 없다

### Requirement: 신청 변경 이력 조회

시스템은 신청 정보·상태·다음 연락 예정의 변경 전후 값·변경자·변경 시각을 보존하고 신청 조회 권한에 따라 확인하게 해야 한다(SHALL). 상담 기록의 작성과 신청 변경을 함께 저장하는 경우 전부 성공하거나 전부 취소해야 한다(SHALL). 이력 편집·삭제·과거 상태 복원을 제공하지 않아야 한다(SHALL).

#### Scenario: 신청 정정과 재연락 일정 변경
- **WHEN** 관리자가 신청 내용과 다음 연락 일정을 변경한다
- **THEN** 변경자·시각·전후 값을 조회할 수 있으며 공개 API에는 이력이 노출되지 않는다

#### Scenario: 기록 저장 실패와 이력 복원 시도
- **WHEN** 상담·변경 이력 저장이 실패하거나 과거 상태 복원을 직접 요청한다
- **THEN** 실패한 변경은 부분 저장되지 않고 복원 요청은 거부한다

#### Scenario: 기존 신청의 이력 시작
- **WHEN** 이 기능 도입 전 신청의 이력을 조회한다
- **THEN** 도입 시점의 기준 상태와 이후 변경을 확인하고 알 수 없는 과거 작성자·변경 사실을 만들어 표시하지 않는다

### Requirement: 안내 처리 기록 조회 전용 관리

시스템은 자동 안내·개별 발송 시도·공유 전송 예산을 권한에 따라 조회만 가능하게 해야 한다(SHALL). 신청 상세에서 안내 상태·예정 시각·시도 횟수·처리 결과를 확인하고 개발 모의 처리·SES 접수·실제 전달을 구분해야 한다(SHALL). 내부 기록의 수동 생성·수정·삭제·재발송은 제공하지 않아야 한다(SHALL).

#### Scenario: 내부 처리값 변경 시도
- **WHEN** 관리자 화면이나 직접 POST로 안내·발송 시도·예산을 변경하려 한다
- **THEN** 쓰기를 거부하고 기존 처리권·전송 증거·속도 제한을 유지한다
