# Spec Delta

## MODIFIED Requirements

### Requirement: 같은 제출의 반복 처리 보호

시스템은 동일한 제출 식별자와 동일한 정규화 입력의 재요청을 기존 접수 결과로 처리해야 한다(SHALL). 동시 요청도 신청과 안내 대상을 한 번만 생성해야 한다(SHALL). 동일 식별자에 다른 입력은 충돌로 거부하고 이메일 주소만으로 서로 다른 신청을 합치지 않아야 한다(SHALL). 비교는 관리자가 수정한 현재 값이 아닌 불변의 최초 제출 입력을 기준으로 해야 한다(SHALL). 공개 응답은 관리자 진행 상태와 무관하게 최초 접수 식별자와 접수 상태만 반환해야 한다(SHALL).

#### Scenario: 응답 유실 후 재제출과 동시 POST
- **WHEN** 이미 저장된 제출을 응답 유실로 다시 보내거나 동일 제출을 동시에 보낸다
- **THEN** 최초 생성은 201, 기존 결과 재사용은 200이고 신청·안내 대상은 각각 하나이며 같은 접수 식별자·상태를 반환한다

#### Scenario: 식별자 재사용 충돌
- **WHEN** 동일한 식별자로 다른 입력을 제출한다
- **THEN** 409를 반환하고 기존 데이터는 변경하지 않으며 기존 신청자의 개인정보를 응답하지 않는다

#### Scenario: 저장 후 날짜 경과 또는 교육 변경
- **WHEN** 동일한 식별자·정규화 입력으로 재요청하며 연락 날짜가 과거가 됐거나 교육이 중단·slug 변경·삭제됐다
- **THEN** 저장 당시 교육 slug와 입력을 비교해 기존 접수 결과를 200으로 반환하고 현재 교육·날짜 조건 때문에 기존 접수 확인을 거부하거나 안내를 추가 생성하지 않는다

#### Scenario: 관리자 정정과 상태 변경 이후 재시도
- **WHEN** 관리자가 이름·이메일·주소·날짜·진행 상태를 바꾼 이후 원래 제출을 재시도한다
- **THEN** 200과 원래 request_id·status=received·status_display=접수만 반환하고 현재 관리값을 덮어쓰지 않으며 상담 상태·취소 사유·이력을 공개하지 않는다

#### Scenario: 정정된 내용으로 식별자 재사용
- **WHEN** 원래 제출 식별자에 관리자가 정정한 내용을 넣어 원본과 다른 입력을 제출한다
- **THEN** 현재 관리값과 같더라도 409로 거부하고 원본·관리값·안내를 변경하지 않는다
