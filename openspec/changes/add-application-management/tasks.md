# Tasks

## 1. 이력 의존성과 보존 가능한 데이터 구조

- [ ] 1.1 `django-simple-history` 3.13 계열을 공통 의존성·lockfile·공통 settings에 연결하고 신청에만 적용한다. `uv sync --locked`·Django check로 로딩을 확인하고 아키텍처 문서의 기술 선택·의존성을 갱신한다.
- [ ] 1.2 신청 상태·다음 연락 예정·취소 사유·최초 제출 snapshot과 상담 기록 모델을 추가하고 신청·상담 일반 삭제 및 기존 상담 수정 경로를 제한한다. PostgreSQL 모델 테스트로 상태·정정 연결·작성자·개별/QuerySet 삭제 차단과 교육 삭제 후 보존을 검증한다.
- [ ] 1.3 후속 schema/data migration으로 기존 신청의 snapshot과 도입 시점 기준 history를 backfill한다. 기존 교육·신청·안내·발송 시도 보존, 과거 작성자 미생성, 새 DB 적용을 migration 테스트와 `makemigrations --check --dry-run`으로 확인한다. 운영 가이드에 maintenance 적용·역적용 손실·전진 수정 기준을 기록한다.

## 2. 원본 접수 계약과 변경 이력

- [ ] 2.1 신규 신청에 정규화 원본 snapshot을 저장하고 `_reuse()`를 원본 비교로 변경한다. `test_api`에 관리자 정정 후 원본 재요청 200·현재 관리값 유지·원본과 다른 입력 409·기존 동시 제출 1건 보존 테스트를 추가해 통과시킨다.
- [ ] 2.2 공개 접수 응답을 최초 received/접수로 고정한다. 완료·취소·재연락 상태에서도 request_id와 접수 응답만 반환하고 목록·개별 조회·수정·취소 API가 공개되지 않음을 `test_api`에서 확인한다. 기능 검증 가이드의 재시도·응답 계약을 갱신한다.
- [ ] 2.3 신청 수정에 history 사용자·시각·전후 값과 transaction을 연결하고 교육 삭제의 FK 해제도 누락 없이 추적한다. 실제 DB 테스트로 정보·상태·일정·교육 연결 변경 이력과 history 저장 실패 시 전체 rollback을 확인하고 아키텍처에 포착 경로와 bulk/직접 SQL 제한을 명시한다.

## 3. 관리 변경과 자동 안내의 정합성

- [ ] 3.1 신청 정정·상태·상담 기록·안내 변경을 같은 transaction의 관리 저장 연산으로 묶고 안내→신청 lock 순서를 worker claim과 통일한다. 안내·history·상담 저장 실패를 주입한 실제 DB 테스트로 부분 저장이 남지 않음을 확인한다.
- [ ] 3.2 미처리 안내의 날짜 정정은 기존 대상의 due_at을 갱신하고 이름·수신자를 최신 값으로 사용한다. `test_notifications`에서 pending/queued/retry_wait별 날짜·이메일 변경, 새 대상 시각 이전 전송 차단, 시도 횟수·다음 재시도 시각 보존을 검증한다.
- [ ] 3.3 suppressed 상태와 완료·취소 시 중단 처리를 추가하고 등록·claim·복구·후속 검사에서 종료 대상을 제외한다. 이미 큐에 있는 작업, stale 복구, 종료 후 상담 재개에서도 발송·새 시도·자동 재개가 없음을 검증한다.
- [ ] 3.4 sending 중 이름·이메일·연락 날짜 정정과 완료·취소를 거부하고 주소·상담·재연락 일정 변경은 허용한다. TransactionTestCase의 별도 DB 연결과 동기화 신호로 관리 저장 우선/claim 우선 경합을 재현하고 외부 전송 횟수·저장 상태를 검증한다.
- [ ] 3.5 accepted/simulated/unknown/failed의 증거 보존과 기존 stale sending·늦은 성공·재시도 한도를 재검증한다. 재연락 일정만 바꿨을 때 안내에 영향이 없는 테스트를 추가하고 운영 가이드에 중단·발송 중 제한·재발송 미지원 정책을 기록한다.
