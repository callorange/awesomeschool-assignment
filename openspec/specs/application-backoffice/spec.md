# application-backoffice Specification

## Purpose

교육 상담 담당자가 별도 백오피스에서 권한에 따라 신청을 조회·정정하고 상담과 재연락 일정을 관리하게 한다. 기존 Django admin과 같은 데이터·인증을 공유하면서 신청별 이메일 처리 현황을 실제 전달 여부와 구분하여 확인하게 한다.

## Requirements

### Requirement: 독립된 진입점과 기존 관리자 공존

시스템은 `/backoffice/` 아래에 담당자용 로그인·신청 목록·상세 화면을 제공하고 `/admin/`의 기존 기능과 주소를 유지해야 한다(SHALL). 백오피스에서 Django admin으로 이동할 수 있고 실행 안내에는 두 주소와 용도를 명시해야 한다(SHALL).

#### Scenario: 두 화면에서 같은 신청 확인
- **WHEN** 권한 있는 관리자가 백오피스에서 신청을 변경한 뒤 Django admin에서 해당 신청을 연다
- **THEN** 같은 변경 결과와 변경 이력이 표시되고 기존 admin 관리 기능이 유지된다

### Requirement: 관리자 인증과 공유 세션

시스템은 기존 계정으로 로그인·로그아웃을 제공하고 활성 staff만 백오피스 업무 화면에 접근하게 해야 한다(SHALL). 두 관리자 화면은 로그인 세션을 공유하고 로그아웃은 POST와 CSRF 검증을 요구해야 한다(SHALL). 로그인 후 안전한 같은 사이트의 복귀 주소 또는 신청 목록으로 이동해야 한다(SHALL).

#### Scenario: 미인증과 관리자 아닌 사용자
- **WHEN** 비로그인 사용자가 업무 화면을 GET으로 조회하거나 비활성·일반 사용자 계정으로 백오피스 로그인을 시도한다
- **THEN** 비로그인은 로그인 화면으로 이동하며 비활성·일반 사용자에게 업무 접근을 허용하지 않고 개인정보를 표시하지 않는다

#### Scenario: 로그인 복귀와 공유 로그아웃
- **WHEN** 상세 화면 접근 후 로그인하거나 어느 관리자 화면에서 정상 로그아웃한다
- **THEN** 로그인 후 원래 상세로 복귀하며 로그아웃 후에는 두 화면 모두 재인증이 필요하고 외부 복귀 주소로 이동하지 않는다

### Requirement: 모델별 작업 권한

시스템은 신청 조회·변경, 상담 조회·추가, 이메일 조회 권한을 각각 확인하고 직접 요청에도 적용해야 한다(SHALL). 상담 접근은 부모 신청 조회 권한도 요구해야 한다(SHALL). 권한이 없는 영역의 데이터를 응답에 포함하지 않고 허용되지 않은 쓰기를 거부해야 한다(SHALL).

#### Scenario: 조회 전용과 숨겨진 정보 접근
- **WHEN** 신청 조회만 가능한 담당자가 상세를 열거나 변경·상담 추가를 직접 POST한다
- **THEN** 신청 조회만 허용하고 쓰기는 거부하며 상담·이메일 조회 권한이 없다면 해당 데이터는 응답에 포함하지 않는다

#### Scenario: 상담만 추가 가능한 담당자
- **WHEN** 신청 조회·상담 추가 권한은 있지만 신청 변경 권한은 없는 담당자가 상담을 등록한다
- **THEN** 상담만 추가하고 신청 값 변경은 허용하지 않으며 상담 기록 조회는 별도 조회 권한에 따른다

### Requirement: 신청 목록 검색과 필터

시스템은 신청 당시 교육명·이름·이메일·연락 가능 날짜·상태·다음 연락 예정·신청 시각을 최신 신청 순의 페이지 단위 목록으로 제공해야 한다(SHALL). 이름·이메일 검색, 교육·상태 및 오늘 재연락·기한 경과·일정 미정 필터를 제공하고 페이지 이동 시 조건을 유지해야 한다(SHALL).

#### Scenario: 검색과 재연락 대상 조회
- **WHEN** 담당자가 검색·필터를 적용하고 다음 페이지로 이동한다
- **THEN** 조건에 해당하는 신청만 표시하고 조건을 유지하며 빈 결과도 오류 없이 안내한다

#### Scenario: 교육 원본 삭제 이후 조회
- **WHEN** 원본 교육이 삭제된 신청을 목록이나 상세에서 확인한다
- **THEN** 신청 당시 교육명으로 확인하고 해당 교육명으로 필터링할 수 있다

### Requirement: 신청 정정과 보존 정책

시스템은 기존 검증에 따라 신청 개인정보·연락 가능 날짜·상태·재연락 일정·취소 사유를 정정하고 변경자와 이력을 보존해야 한다(SHALL). 최초 제출 정보·식별자·교육 snapshot·접수 시각은 변경하지 않아야 한다(SHALL). 신청 수동 생성·삭제와 이력 복원을 제공하지 않아야 한다(SHALL).

#### Scenario: 일정과 종료 상태 변경
- **WHEN** 담당자가 재연락 일정 또는 완료·취소 상태를 저장한다
- **THEN** 새 과거 일정과 사유 없는 취소는 거부하고 기존 기한 경과 일정의 유지 및 종료 시 현재 일정 정리는 기존 정책대로 처리한다

#### Scenario: 입력 오류와 보호 필드 변조
- **WHEN** 잘못된 이메일·우편번호 등을 입력하거나 최초 제출 정보·삭제를 직접 요청한다
- **THEN** 유효하지 않은 변경과 삭제는 저장되지 않고 일반 입력 오류는 필드 오류와 수정 입력을 유지해 다시 표시한다

### Requirement: 상담 누적과 원자적 저장

시스템은 신청별 상담 결과·내용·작성자·시각·당시 재연락 일정을 표시하고 권한에 따라 새 상담을 추가해야 한다(SHALL). 기존 기록의 수정·삭제 대신 같은 신청의 원기록을 가리키는 정정을 제공해야 한다(SHALL). 신청 정정과 상담을 함께 제출하면 모두 저장되거나 모두 취소되어야 한다(SHALL).

#### Scenario: 신청과 상담 동시 저장
- **WHEN** 담당자가 신청 상태·일정을 변경하면서 상담을 추가한다
- **THEN** 같은 저장에서 신청·이력·안내 조정·상담이 함께 확정되고 상담 작성자와 변경 후 일정은 서버 값으로 기록된다

#### Scenario: 잘못된 상담과 저장 실패
- **WHEN** 명시적으로 상담 추가를 요청했지만 필수 입력이 없거나 다른 신청 기록을 정정 대상으로 지정하거나 저장 중 실패한다
- **THEN** 신청 정정과 새 상담을 부분 저장하지 않고 다른 신청 기록을 노출하지 않으며 유효성 오류 시 입력을 유지한다

### Requirement: 권한별 저장 의도와 상담 추가 선택

시스템은 신청 변경 권한에 따라 수정 폼과 '변경사항 저장'을 제공하고 상담 추가만 가능하면 신청 읽기 전용과 '상담 추가'를 제공해야 한다(SHALL). 통합 저장의 '상담 기록도 추가'는 기본 해제하며 선택한 경우에만 상담 결과·내용을 필수 검증해야 한다(SHALL). 상담 추가 전용 요청은 항상 필수 검증하고 서버에서도 작업별 권한을 검사해야 한다(SHALL).

#### Scenario: 신청만 저장하거나 상담을 함께 저장
- **WHEN** 담당자가 상담 추가를 선택하지 않고 신청을 저장하거나 상담 추가를 선택해 제출한다
- **THEN** 미선택은 신청만 저장하며 선택한 경우 결과·내용이 모두 유효해야 신청과 상담을 함께 저장하고 오류 시 선택 상태와 입력을 유지한다

#### Scenario: 상담 추가 전용과 잘못된 작업 요청
- **WHEN** 담당자가 상담 추가 전용으로 빈 상담을 제출하거나 신청 변경 권한 없이 통합 저장하거나 알 수 없는 작업을 요청한다
- **THEN** 빈 상담·권한 없는 저장·알 수 없는 작업을 거부하고 신청·상담을 변경하지 않는다

#### Scenario: 상담 조회 권한 없는 정정 요청
- **WHEN** 상담 조회 권한 없이 기존 기록의 정정 결과나 원기록을 직접 지정해 제출한다
- **THEN** 정정을 거부하고 기존 상담 내용을 노출하지 않으며 일반 상담 추가는 해당 추가 권한에 따라 허용한다

### Requirement: 이메일 상태 조회 전용 표시

시스템은 이메일 조회 권한이 있는 담당자에게 신청 상세에서 처리 상태·모드·예정 시각·모의 완료/SES 접수 시각·시도 횟수·안전한 오류 코드를 표시해야 한다(SHALL). 모의 완료·SES 접수·결과 확인 필요·발송 중단을 구분하고 실제 전달 완료로 표시하지 않아야 한다(SHALL). 재발송·task 제어·내부 처리값 변경은 제공하지 않아야 한다(SHALL).

#### Scenario: 처리 결과 구분
- **WHEN** 모의 완료·SES 접수·실패·결과 불명·발송 중단 신청을 확인한다
- **THEN** 저장된 상태에 맞게 표시하고 SES 접수를 수신함 도착으로 표현하거나 결과 불명을 미발송으로 단정하지 않는다

#### Scenario: 발송 중 신청 변경과 내부값 조작
- **WHEN** 발송 중 이름·이메일·연락 날짜나 종료 상태를 변경하거나 이메일 내부값·재발송을 요청한다
- **THEN** 발송 중 제한 대상 변경과 내부 처리값 조작을 거부하고 기존 전송 증거를 유지하며 추가 발송하지 않는다

### Requirement: 페이지 이동과 저장 방식

시스템은 로그인·로그아웃·신청 정정·상담 저장을 일반 POST로, 목록·상세 이동과 검색·필터·페이지네이션을 일반 GET으로 처리해야 한다(SHALL). 검색 조건은 URL에 유지하고 신청·상담 동시 저장은 한 번의 제출에서 처리해야 한다(SHALL). 메뉴·입력 영역 펼치기만으로 서버에 요청하지 않아야 한다(SHALL).

#### Scenario: 조회 조건 복원과 통합 저장
- **WHEN** 담당자가 목록의 조건을 URL로 다시 열거나 신청·상담을 함께 제출한다
- **THEN** 같은 조회 조건이 적용되고 저장은 일반 페이지 요청으로 원자적으로 처리되며 신청 상태만 별도 비동기 저장되지 않는다

### Requirement: 이메일 상태 부분 갱신과 입력 보존

시스템은 상세 최초 조회에 이메일 상태를 표시하고 수동 새로고침 시 Ajax GET으로 이메일 표시 영역만 갱신해야 한다(SHALL). 작성 중인 신청·상담 입력을 유지하고 요청 중 진행 상태와 중복 요청 방지를 제공해야 한다(SHALL). 자동 polling은 제공하지 않고 JavaScript 없이도 최초 상태 조회와 일반 저장이 가능해야 한다(SHALL).

#### Scenario: 작성 도중 상태 확인
- **WHEN** 담당자가 신청이나 상담을 작성하면서 이메일 상태 새로고침을 누른다
- **THEN** 입력과 버튼 focus를 유지한 채 이메일 표시만 최신 상태로 갱신하고 조회로 신청 변경이나 발송을 일으키지 않는다

#### Scenario: 갱신 실패와 세션 만료
- **WHEN** 부분 조회 중 네트워크/서버 오류·세션 만료·권한 거부가 발생한다
- **THEN** 입력과 기존 표시를 유지하며 갱신 실패·재로그인 필요·접근 거부를 구분해 알리고 재로그인은 별도 탭 링크를 제공하며 오류나 로그인 화면을 상태 영역에 삽입하지 않고 자동 이동·저장·재전송하지 않는다

#### Scenario: 권한 없는 부분 조회와 JavaScript 미사용
- **WHEN** 권한 없이 부분 조회를 직접 요청하거나 JavaScript 없이 상세를 사용한다
- **THEN** 부분 조회는 개인정보를 노출하지 않고 거부하며 JavaScript 미사용 시 부분 갱신 불가를 알리되 최초 이메일 상태 조회와 일반 폼 저장은 제공한다

### Requirement: 일반 저장 인증 오류의 미저장 안내

시스템은 일반 업무 저장 POST의 세션 만료·CSRF 실패 시 저장을 거부하고 미저장 및 재로그인 필요를 안내해야 한다(SHALL). 해당 오류의 POST 개인정보를 오류 화면에 재출력하거나 자동 복구·재전송하지 않아야 한다(SHALL). 입력 보존 보장 범위는 일반 유효성 오류와 Ajax 조회 실패로 명시해야 한다(SHALL).

#### Scenario: 저장 시 세션 또는 CSRF 검증 실패
- **WHEN** 만료된 세션이나 잘못된 CSRF token으로 신청 또는 상담을 저장한다
- **THEN** 저장 없이 오류를 안내하고 자동으로 로그인 후 저장을 재개하거나 제출 개인정보를 오류 화면에 표시하지 않는다

### Requirement: 공통 반응형 navigation과 화면 구성

시스템은 desktop에서 사이드바·상단바·본문을, 모바일에서 접이식 메뉴·한 열 본문을 제공해야 한다(SHALL). 업무 화면은 일관된 navigation·페이지 제목·내용 영역과 현재 위치 표시를 제공하고 구현됐으며 권한이 허용된 메뉴만 보여야 한다(SHALL). 목록의 검색·필터·페이지 이동과 상세의 신청·상담·이메일 영역을 구분해야 한다(SHALL).

#### Scenario: 화면 크기에 따른 메뉴와 본문 전환
- **WHEN** 담당자가 desktop 또는 모바일에서 신청 목록·상세를 사용한다
- **THEN** desktop에서는 사이드바를, 모바일에서는 키보드로 열고 닫을 수 있는 메뉴를 사용하며 검색·필터·폼과 본문이 화면 너비에 맞게 배치된다

#### Scenario: 화면 이동과 메뉴 표시
- **WHEN** 담당자가 신청 목록에서 상세로 이동하거나 업무 navigation을 확인한다
- **THEN** 공통 navigation과 페이지 제목의 배치가 유지되고 현재 신청 관리 위치가 표시되며 미구현 기능이나 권한 없는 메뉴는 표시되지 않는다

### Requirement: 업무 화면 사용성과 재제출 방지

시스템은 모바일과 desktop에서 로그인·목록·상세의 내용과 폼을 사용할 수 있고 키보드로 접근 가능한 label·focus·오류 안내를 제공해야 한다(SHALL). 저장 성공은 상세 조회로 이동해 알리고 새로고침만으로 상담이 다시 추가되지 않아야 한다(SHALL).

#### Scenario: 작은 화면과 저장 후 새로고침
- **WHEN** 작은 화면이나 키보드로 폼을 사용하고 정상 저장 후 새로고침한다
- **THEN** 페이지 전체의 가로 넘침 없이 내용과 오류를 확인할 수 있고 동일 상담이 새로 추가되지 않는다
