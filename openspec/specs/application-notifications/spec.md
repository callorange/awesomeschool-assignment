# application-notifications Specification

## Purpose

연락 가능 날짜에 신청자에게 상담 접수 안내를 전달하고, 개발 모의 처리와 운영 발송 결과를 구분해 추적하게 한다. 작업 중단·중복 실행·외부 응답 유실이 발생해도 미처리 대상을 보존하고 확인되지 않은 메일을 무조건 다시 보내지 않는다.

## Requirements

### Requirement: 날짜별 안내 대상과 지연 복구

신청과 함께 안내 대상 하나를 pending·시도 횟수 0으로 영속 보관하고 아직 시도 기록·접수 시각·SES MessageId를 만들지 않아야 한다(SHALL). 연락 가능 날짜의 한국 시간 09시부터 5분 주기로 미처리 대상을 확인하고 이미 09시가 지난 당일 신청은 다음 검사에서 대상이 돼야 한다(SHALL). 중단 중 날짜가 지나도 미처리 대상을 버리지 않아야 한다(SHALL). 관리자가 완료·취소한 신청의 미처리 안내는 발송 중단으로 보존하고 신규 등록·처리권 확보에서 제외해야 한다(SHALL).

#### Scenario: 신규 안내와 큐 대기
- **WHEN** 신청이 생성된 후 안내가 큐에 등록되지만 worker가 아직 발송을 시작하지 않았다
- **THEN** 신규 안내는 pending·시도 0으로 생성되고 큐 등록 후 queued가 되어도 시도 0·시도 기록 없음·접수 시각 없음·MessageId 없음이 유지된다

#### Scenario: 예약 전과 당일 늦은 접수
- **WHEN** 연락 가능 날짜 09시 전이거나 당일 09시 이후 신규 접수된다
- **THEN** 09시 전에는 발송하지 않고 당일 늦은 접수는 다음 정상 검사에서 대상이 된다

#### Scenario: 시스템 중단과 큐 등록 실패
- **WHEN** 예정 시각에 시스템이 중단되거나 큐 등록이 실패한 뒤 복구된다
- **THEN** DB의 미처리 대상이 다음 검사에서 재발견되고 이미 처리된 대상은 새로 발송하지 않는다

#### Scenario: 대기 안내의 완료와 취소
- **WHEN** pending·queued·retry_wait 안내가 있는 신청을 관리자가 완료 또는 사유 있는 취소로 저장한다
- **THEN** 안내를 발송 중단으로 보존하고 이미 등록된 작업·복구 검사도 외부 전송이나 새 시도 기록을 만들지 않는다

### Requirement: 상담 안내 템플릿

안내는 한국어 제목·HTML·일반 텍스트를 함께 제공해야 한다(SHALL). 신청자명·신청 당시 교육명·연락 가능 날짜·상담 후 조건 협의 안내를 포함하고 교육 일정이나 실제 연락 시각을 확약하지 않아야 한다(SHALL). 지연 발송에서도 날짜를 사실대로 표현하며 주소 등 불필요한 개인정보를 포함하지 않아야 한다(SHALL).

#### Scenario: 정상 안내와 지연 안내
- **WHEN** 해당 날짜 또는 시스템 복구 후 뒤늦게 안내를 생성한다
- **THEN** 선택 날짜를 명시하고 이미 지난 날짜를 오늘이라고 표현하지 않으며 HTML 입력은 escape하고 텍스트 대안도 제공한다

### Requirement: 환경별 발송 경계

개발과 운영은 공통 Django 이메일 API를 사용하고 환경별 backend 설정으로 발송 경계를 구분해야 한다(SHALL). 개발은 외부 전송·AWS 연결 없이 모의 처리 기록을 완료하고 운영은 AWS SES로 발송해 API 접수 성공·실패·결과 불명을 구분해야 한다(SHALL). 개발 모의 완료를 운영 접수 성공으로 취급하지 않아야 한다(SHALL).

#### Scenario: 개발 처리 반복
- **WHEN** 개발 worker가 같은 안내를 반복 실행한다
- **THEN** 실제 외부 전송은 없고 모의 완료가 한 번 기록되며 발송 성공 시각·SES MessageId는 생성되지 않는다

#### Scenario: 운영 발송 설정 누락
- **WHEN** 운영 발신자·리전 등 필수 발송 설정이 누락된다
- **THEN** 운영 설정 오류로 중단하고 모의 전송이나 다른 메일 전송 방식으로 자동 전환하지 않는다

### Requirement: 중복 실행의 발송 제어

동일 신청의 동일 안내 대상은 하나여야 하고, 여러 작업·worker·주기 검사가 겹쳐도 한 시도만 발송 처리권을 가져야 한다(SHALL). 발송 직전 시도 식별자와 처리 상태를 영속 보관하고 성공 후 SES 접수 시각·MessageId를 기록해야 한다(SHALL). 접수 성공·모의 완료·결과 불명 대상은 일반 재실행에서 전송하지 않아야 한다(SHALL).

#### Scenario: 동시 worker와 완료 작업 재실행
- **WHEN** 같은 안내를 여러 worker가 동시에 실행하거나 접수 성공한 작업을 다시 등록한다
- **THEN** 한 worker만 발송을 시도하고 이후 실행은 외부 전송을 생략하며 접수 기록을 유지한다

#### Scenario: 발송 중 worker 종료
- **WHEN** 영속 처리권 확보 후 성공·실패 기록 전에 worker가 종료된다
- **THEN** 남은 시도는 결과 확인 필요로 보존되고 작업 재전달만으로 새로운 전송을 시작하지 않는다

### Requirement: 오류별 재시도와 실패 이력

미접수가 확정된 일시적 오류만 지연 재시도해야 한다(SHALL). 일반 일시 오류는 첫 실패 후 5분·두 번째 실패 후 15분, 일일 한도 초과는 각 실패 후 24시간을 재시도 가능 시각으로 정해야 한다(SHALL). 최초 포함 총 3회로 제한하고 오류 종류가 바뀌어도 횟수를 초기화하지 않아야 한다(SHALL). 설정·인증·유효성 오류와 결과 불명은 자동 재발송하지 않고 안전한 오류 코드·시도·다음 시각을 추적해야 한다(SHALL).

#### Scenario: 일시적 발송 제한
- **WHEN** SES가 미접수가 명확한 일시적 발송 제한으로 거부한다
- **THEN** 첫 실패 후 5분, 두 번째 실패 후 15분부터 재시도 가능하고 실제 실행은 검사·큐 상황에 따라 늦어질 수 있으며 세 번째 실패 후 자동 시도하지 않는다

#### Scenario: 일일 한도 초과
- **WHEN** SES가 일일 한도 초과로 미접수를 명확히 응답한다
- **THEN** 이번 시도를 기록하고 다음 시각을 실패 후 24시간으로 정하며 앞선 오류와 합쳐 세 번째 실패이면 failed로 보존하고 자동 재시도하지 않는다

#### Scenario: 설정 오류와 응답 유실
- **WHEN** 권한·발신자 설정 오류가 있거나 요청 후 응답이 유실된다
- **THEN** 설정 오류는 조치 필요, 응답 유실은 결과 확인 필요로 구분하며 둘 다 무조건 재발송하지 않고 실패 원문·개인정보를 작업 관리 목록에 노출하지 않는다

### Requirement: API 접수 결과와 확인 범위

운영 발송의 성공은 SES API가 반환한 접수 응답과 MessageId로 판단하고 실제 전달 성공으로 표시하지 않아야 한다(SHALL). 응답 유실·접수 후 기록 실패의 결과 불명은 확인 필요로 보존하고 자동 재발송하거나 근거 없이 성공·미발송으로 판정하지 않아야 한다(SHALL). 이번 범위에서는 SNS·웹훅·이벤트 수집과 실제 전달·반송 확인을 제공하지 않아야 한다(SHALL).

#### Scenario: API 접수 성공
- **WHEN** SES API가 성공과 MessageId를 반환한다
- **THEN** 해당 시도의 접수 시각·MessageId를 기록하고 중복 실행에서 다시 보내지 않으며 실제 수신함 도착이나 전달 성공으로 표시하지 않는다

#### Scenario: backend의 비정상 반환
- **WHEN** 운영 backend가 0을 반환하거나 1을 반환했지만 MessageId가 없다
- **THEN** 0이고 외부 미전송이 확실하면 failed로 기록하며 접수 증거 누락·불일치 또는 미전송이 불확실하면 unknown으로 보존하고 자동 재발송하지 않는다

#### Scenario: 결과 불명의 장기 보존
- **WHEN** API 응답이 유실되거나 접수 후 결과 저장이 실패한 시도에 대해 시간이 지나거나 작업이 재전달된다
- **THEN** 확인 필요 기록을 유지하고 자동 재발송하지 않으며 시간 경과만으로 성공·미발송으로 변경하지 않는다

#### Scenario: 이벤트 인프라 없이 운영 발송
- **WHEN** 필수 SES 발송 설정이 준비됐지만 SNS topic·웹훅·이벤트 수집 설정이 없다
- **THEN** API 발송과 접수 결과 기록은 동작하고 실제 전달·반송 확인은 제공하지 않는다

### Requirement: 발송량 분산과 속도 제한

날짜별 검사와 개별 발송을 분리하고 due_at·PK 순으로 batch당 최대 100건을 등록해야 한다(SHALL). 실행 시간·메일 큐 적체를 제한하되 남은 대상과 여유가 있으면 다음 batch를 이어 처리해야 한다(SHALL). 여러 worker의 전체 전송 속도를 설정된 SES 계정 한도 이하로 공유 제어하고 미처리 대상을 버리거나 관리자가 정한 신청 상태를 변경하지 않아야 한다(SHALL).

#### Scenario: 다수 신청의 처리
- **WHEN** 같은 날짜의 신청이 많고 두 worker가 발송한다
- **THEN** 건별 작업을 나누어 처리하고 전체 속도 제한을 공유하며 아직 보내지 못한 대상은 DB에 남고 신청 상태는 처리 전 값을 유지한다

#### Scenario: 여러 batch와 처리 중단
- **WHEN** 도래한 대상이 100건을 초과하고 등록 여유가 있거나 검사 실행 예산을 소진한다
- **THEN** 오래된 대상부터 100건 이하씩 이어 등록하고 실행 예산 소진 시 여유가 있으면 후속 검사를 등록하며 여유 부족·후속 등록 실패·중단에도 다음 정기 검사로 대상을 복구한다

### Requirement: 복구 상태 전이와 결과 기록 보호

만료된 queued·sending 복구를 신규 등록보다 먼저 수행해야 한다(SHALL). 전송 예산 미확보는 시도 증가 없이 대기로 돌리고 결과는 현재 attempt_id·예상 상태가 일치할 때 시도와 안내에 함께 저장해야 한다(SHALL). accepted·simulated는 중복·늦은 실패로 변경하지 않고 unknown은 같은 시도의 뒤늦은 성공 응답과 MessageId가 있을 때만 accepted로 복구해야 한다(SHALL).

#### Scenario: 전송 예산 미확보와 만료 상태 복구
- **WHEN** queued 대상이 예산을 얻지 못하거나 queued·sending이 10분 이상 남는다
- **THEN** 예산 미확보는 retry_wait·다음 허용 시각으로 옮기되 시도 증가·새 시도 기록은 없고 만료 queued는 pending으로 복구하며 만료 sending은 unknown으로 보존한다

#### Scenario: 늦은 결과와 결과 저장 장애
- **WHEN** 이미 완료된 안내에 이전 실행의 실패가 도착하거나 현재 시도의 접수 성공 뒤 DB 저장이 실패한다
- **THEN** accepted·simulated를 덮어쓰지 않고 현재 attempt_id의 결과만 반영하며 저장 장애는 재발송하지 않고 남은 sending을 이후 unknown으로 복구한다

#### Scenario: 같은 시도의 늦은 성공 응답
- **WHEN** unknown으로 전환된 현재 시도의 API 성공 응답·MessageId가 뒤늦게 기록된다
- **THEN** 외부 호출을 추가하지 않고 해당 시도와 안내를 accepted로 함께 갱신한다

### Requirement: 신청 정정과 미처리 안내 일관성

시스템은 pending·queued·retry_wait 안내의 발송에 최신으로 정정한 이름·이메일·연락 가능 날짜를 사용하고 날짜 정정 시 기존 안내의 대상 시각을 함께 조정해야 한다(SHALL). 시도 횟수·재시도 대기·전송 증거는 초기화하지 않아야 한다(SHALL). 신청·이력·안내 조정은 함께 성공하거나 취소돼야 한다(SHALL).

#### Scenario: 큐 등록 뒤 날짜와 이메일 정정
- **WHEN** worker가 처리권을 얻기 전에 이메일과 연락 가능 날짜를 미래로 정정한다
- **THEN** 이미 등록된 작업도 새 대상 시각 전에는 발송하지 않고 이후 정정된 이메일로 처리하며 안내를 추가 생성하지 않는다

#### Scenario: 재시도 대기 중 날짜 변경
- **WHEN** 재시도 대기 안내의 연락 가능 날짜를 정정한다
- **THEN** 새 대상 시각과 기존 재시도 허용 시각을 모두 충족해야 발송하고 누적 횟수와 이전 시도 기록을 유지한다

### Requirement: 발송 중 수정과 종료의 경계

시스템은 발송 처리권 확보와 관리 변경을 직렬화해야 한다(SHALL). sending 동안 이름·이메일·연락 가능 날짜 정정과 신청 완료·취소 처리를 거부하고 처리 결과 기록 또는 기존 만료 복구 이후 재시도하도록 안내해야 한다(SHALL). 외부 전송 뒤 전송 취소나 미발송을 보장했다고 표시하지 않아야 한다(SHALL).

#### Scenario: 발송 처리권과 취소의 경합
- **WHEN** worker 처리권 확보와 관리자의 취소 저장이 동시에 발생한다
- **THEN** 취소가 먼저 확정되면 전송하지 않고 처리권 확보가 먼저면 취소 저장을 거부하며 결과 확인 후 다시 처리하도록 안내한다

#### Scenario: 이미 처리된 안내가 있는 신청 정정과 종료
- **WHEN** accepted·simulated·unknown·failed 안내가 있는 신청을 정정하거나 완료·취소한다
- **THEN** 신청 변경은 기록하되 기존 결과·시도·전송 증거는 변경하지 않고 메일을 새로 보내지 않는다

### Requirement: 재연락 일정과 자동 안내의 분리

시스템은 다음 연락 예정 변경과 상담 기록 추가만으로 기존 연락 가능 날짜·안내 대상 시각을 바꾸거나 추가 안내를 만들지 않아야 한다(SHALL). 발송 중단된 신청을 다시 상담중·재연락 예정으로 바꿔도 안내를 자동 재개하지 않아야 한다(SHALL).

#### Scenario: 재연락 일정 변경과 상담 재개
- **WHEN** 다음 연락 예정 일시를 여러 번 바꾸거나 종료 후 상담을 재개한다
- **THEN** 일정·변경 기록은 보존하되 자동 안내의 신규 생성·재발송·자동 재개는 발생하지 않는다
