# education-applications Specification

## Purpose

방문자가 선택한 교육의 상담 신청을 모바일과 데스크톱에서 완료하고 접수 결과를 확인하게 한다. 주소 검색과 비동기 입력을 지원하되 실제 저장 여부는 서버 검증과 영속 데이터로 판단하고 신청자의 개인정보를 공개하지 않는다.

## Requirements

### Requirement: 교육별 신청 페이지

시스템은 `/educations/<slug>/apply/`에서 선택 교육의 신청 페이지를 공개해야 한다(SHALL). 이름·이메일·주소·연락 가능 날짜 1개를 입력받고 상담 접수임을 안내해야 한다(SHALL). 없는 교육은 404로 처리해야 한다(SHALL).

#### Scenario: 접수 가능한 교육 신청
- **WHEN** 방문자가 접수 가능한 교육의 신청 페이지에 접근한다
- **THEN** 해당 교육을 식별하고 네 가지 입력을 완료할 수 있으며 교육 일정·수강 확정으로 안내하지 않는다

#### Scenario: 없는 교육 또는 접수 중단
- **WHEN** 없는 교육 또는 접수 중단 교육의 신청 페이지를 연다
- **THEN** 없는 교육은 404이고 중단 교육은 중단 안내와 함께 제출이 비활성화되며 교육 소개로 돌아갈 수 있다

### Requirement: 신청용 교육정보 GET

시스템은 `GET /api/educations/<slug>/`에서 `slug`·`title`·`summary`·`image_url`·`image_alt`·`operation_type`·`operation_note`·`is_accepting_inquiries`를 JSON으로 공개해야 한다(SHALL). 신청 화면은 이 응답으로 교육 안내와 제출 가능 상태를 구성해야 한다(SHALL). 신청자 정보·프리셋 수집 기록은 반환하지 않아야 한다(SHALL).

#### Scenario: 교육정보 조회와 실패
- **WHEN** 신청 페이지가 등록 교육의 API를 조회하거나 교육이 없거나 조회에 실패한다
- **THEN** 정상 조회는 200과 교육 안내를 제공하고 없는 교육은 404이며 화면은 조회 실패를 알리고 미확인 상태의 제출을 막는다

### Requirement: 주소 검색과 직접 입력

시스템은 폼 내부 주소 검색에서 우편번호·기본주소를 선택해 입력하고 선택적인 상세주소를 별도 작성하게 해야 한다(SHALL). 검색 취소·외부 서비스 장애에도 기존 입력을 보존하고 직접 입력으로 신청할 수 있어야 한다(SHALL).

#### Scenario: 주소 선택과 상세 입력
- **WHEN** 방문자가 도로명·건물명·지번으로 검색한 결과를 선택한다
- **THEN** 우편번호와 기본주소가 채워지고 검색 영역이 닫히며 상세주소로 포커스가 이동한다

#### Scenario: 주소 검색 취소 또는 장애
- **WHEN** 방문자가 검색을 취소하거나 검색 서비스를 사용할 수 없다
- **THEN** 기존 입력은 유지되고 취소 시 검색 버튼으로 포커스가 돌아가며 직접 입력으로 완료할 수 있다

### Requirement: 입력 검증과 접수 상태 저장

시스템은 `POST /api/applications/`로 `education_slug`·`name`·`email`·`postal_code`·`address`·선택적 `address_detail`·`contact_date`·`request_id`만 받아 검증해야 한다(SHALL). 날짜는 YYYY-MM-DD, 식별자는 UUID이며 연락 가능 날짜는 한국 날짜 기준 오늘을 포함해야 한다(SHALL). 신규 접수는 접수 가능 교육만 허용하고 항상 `접수`로 저장하며 안내 대상을 함께 보존해야 한다(SHALL).

#### Scenario: 정상 신청과 상태 변조 시도
- **WHEN** 유효한 신청을 제출하거나 클라이언트가 별도의 상태값을 보낸다
- **THEN** 정상 입력은 신청과 안내 대상이 함께 생성되어 201과 접수 결과를 반환하고 상태값 입력은 400으로 거부되며 클라이언트가 저장 상태를 정하지 못한다

#### Scenario: 필수값·이메일·날짜 검증
- **WHEN** 필수값이 비거나 길이를 초과하거나 이메일·우편번호 형식이 잘못되거나 날짜가 과거·잘못된 형식이다
- **THEN** 400과 해당 필드의 오류를 반환하고 신청·안내 대상은 생성하지 않는다

#### Scenario: 오늘 날짜와 입력 정규화
- **WHEN** 한국 날짜 기준 오늘을 선택하고 문자열 바깥 공백 또는 생략된 상세주소가 포함된 정상 신청을 보낸다
- **THEN** 오늘을 허용하고 바깥 공백을 제거하며 상세주소 생략은 빈 문자열로 저장하되 이메일 대소문자·주소 내용을 자의적으로 변경하지 않는다

#### Scenario: 화면 표시 후 접수가 중단됨
- **WHEN** 신청 화면 표시 후 교육 접수가 중단되거나 교육이 삭제된 상태에서 POST한다
- **THEN** 서버가 최신 교육 상태를 확인해 중단은 400, 없는 교육은 404로 거부하고 저장하지 않는다

#### Scenario: 영속화 도중 오류
- **WHEN** 신청과 안내 대상 중 하나의 DB 저장이 실패한다
- **THEN** 둘 다 생성되지 않고 클라이언트에 성공을 표시하지 않으며 재시도 가능한 실패 안내를 제공한다

### Requirement: 같은 제출의 반복 처리 보호

시스템은 동일한 제출 식별자와 동일한 정규화 입력의 재요청을 기존 접수 결과로 처리해야 한다(SHALL). 동시 요청도 신청과 안내 대상을 한 번만 생성해야 한다(SHALL). 동일 식별자에 다른 입력은 충돌로 거부하고 이메일 주소만으로 서로 다른 신청을 합치지 않아야 한다(SHALL). 비교는 관리자가 수정한 현재 값이 아닌 불변의 최초 제출 입력을 기준으로 해야 한다(SHALL). 공개 응답은 관리자 진행 상태와 무관하게 최초 접수 식별자와 접수 상태만 반환해야 한다(SHALL).

#### Scenario: 응답 유실 후 재제출과 동시 POST
- **WHEN** 이미 저장된 제출을 응답 유실로 다시 보내거나 동일 제출을 동시에 보낸다
- **THEN** 최초 생성은 201, 기존 결과 재사용은 200이고 신청·안내 대상은 각각 하나이며 같은 접수 식별자·상태를 반환한다

#### Scenario: 식별자 재사용 충돌
- **WHEN** 동일한 식별자로 다른 입력을 제출한다
- **THEN** 409를 반환하고 기존 데이터는 변경하지 않으며 기존 신청자의 개인정보를 응답하지 않는다

#### Scenario: 저장 후 날짜 경과 또는 교육 변경
- **WHEN** 동일한 식별자·정규화 입력으로 재요청하며 연락 날짜가 과거가 됐거나 교육이 중단·slug 변경·삭제됐다
- **THEN** 저장 당시 교육 slug와 입력을 비교해 기존 접수 결과를 200으로 반환하고 현재 교육·날짜 조건 때문에 기존 접수 확인을 거부하거나 안내를 추가 생성하지 않는다

#### Scenario: 관리자 정정과 상태 변경 이후 재시도
- **WHEN** 관리자가 이름·이메일·주소·날짜·진행 상태를 바꾼 이후 원래 제출을 재시도한다
- **THEN** 200과 원래 request_id·status=received·status_display=접수만 반환하고 현재 관리값을 덮어쓰지 않으며 상담 상태·취소 사유·이력을 공개하지 않는다

#### Scenario: 정정된 내용으로 식별자 재사용
- **WHEN** 원래 제출 식별자에 관리자가 정정한 내용을 넣어 원본과 다른 입력을 제출한다
- **THEN** 현재 관리값과 같더라도 409로 거부하고 원본·관리값·안내를 변경하지 않는다
### Requirement: 신청 개인정보와 요청 보호

신청 생성은 로그인 없이 가능해야 하고 익명 요청에도 CSRF를 검사해야 한다(SHALL). 이번 범위의 공개 API는 신청 목록·개별 신청 조회·수정·삭제·상태 변경을 제공하지 않아야 한다(SHALL). 성공 응답에는 접수 식별자·접수 상태만 포함해야 한다(SHALL).

#### Scenario: 토큰 없는 POST와 개인정보 조회
- **WHEN** 유효한 CSRF token 없이 POST하거나 신청 목록을 GET한다
- **THEN** POST는 403, 목록 GET은 405이며 신청 데이터는 변경·노출되지 않는다

#### Scenario: 신청 성공 응답
- **WHEN** 정상 신청 또는 같은 제출의 재시도가 완료된다
- **THEN** request_id·status=received·status_display=접수만 반환하고 내부 PK·이름·이메일·주소는 응답에 포함하지 않는다

### Requirement: 모바일 비동기 제출과 복구

신청 폼은 360px·390px·768px·1280px에서 가로 넘침 없이 사용할 수 있어야 한다(SHALL). 입력 label·오류 연결·16px 이상 입력 글자·44px 이상 주요 터치 영역·이메일 자동완성을 제공해야 한다(SHALL). 제출 중 편집·재클릭을 막고 결과 미확인 시 원래 입력·식별자를 함께 보존해 동일 제출만 재시도해야 한다(SHALL).

#### Scenario: 오류와 통신 실패 후 재시도
- **WHEN** 입력 오류 또는 통신 실패가 발생한다
- **THEN** 필드 오류는 첫 오류로 포커스를 이동하고 미저장 확정 시 입력 수정을 허용하며 통신 실패는 저장 여부 미확인으로 안내해 원래 payload·식별자로만 재시도한다

#### Scenario: 서버 저장 후 응답 유실과 입력 변경 시도
- **WHEN** 신청은 저장됐지만 응답이 유실된 뒤 방문자가 입력을 바꾸거나 재시도하려 한다
- **THEN** 현재 페이지에서 편집을 막고 원래 payload·식별자의 재시도만 제공하며 200으로 기존 접수를 확인하고 신청·안내는 각각 한 건이다

#### Scenario: 확정 오류와 식별자 충돌
- **WHEN** 서버가 미저장 확정인 400/404 또는 최초 요청의 CSRF 403을 반환하거나 식별자 충돌 409를 반환한다
- **THEN** 미저장 확정이면 편집과 다음 제출의 새 ID 생성을 허용하고 409이면 ID·원래 입력을 보존해 충돌을 알리며 새 ID로 자동 전송하지 않는다

#### Scenario: 결과 미확인 요청 재시도 중 CSRF 만료
- **WHEN** 이전 제출 결과를 모르는 상태에서 같은 요청을 재시도하다 CSRF 403을 받는다
- **THEN** 이전 제출의 미저장을 확정하지 않고 ID·payload를 유지하며 token 갱신 후 같은 제출을 재시도한다

#### Scenario: 제출 성공과 모바일 입력
- **WHEN** 모바일 키보드·주소 검색·기본 날짜 선택기로 입력한 뒤 신청한다
- **THEN** 페이지 전체 새로고침 없이 진행 상태와 접수 완료를 확인하고 중복 클릭을 막으며 상태 안내는 보조기술에서도 인식할 수 있다
