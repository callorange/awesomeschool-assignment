# education-catalog Specification

## Purpose

방문자가 로그인 없이 서비스의 교육 목적과 제공 프로그램을 파악하고, 관심 교육의 목표·대상·커리큘럼을 상세히 확인할 수 있게 한다. 모바일부터 데스크톱까지 동일한 교육 정보를 읽고 탐색할 수 있도록 보장한다.

## Requirements

### Requirement: 공개 랜딩에서 교육 탐색
시스템은 `/`에서 서비스 소개와 교육별 이름·한 줄 소개·대표 이미지·상세 링크를 제공해야 한다(SHALL). 로그인 없이 접근할 수 있어야 한다(SHALL).

#### Scenario: 초기 교육 탐색
- **WHEN** 초기 데이터가 설정된 상태에서 익명 방문자가 `/`에 접근한다
- **THEN** HTTP 200으로 서비스 소개와 프롬프트·감정탐험·관계 히어로 카드가 표시되고 각 링크가 해당 상세로 연결된다

#### Scenario: 교육 데이터가 없는 상태
- **WHEN** 교육이 없는 상태에서 `/`에 접근한다
- **THEN** HTTP 200으로 서비스 소개와 교육 준비 안내를 표시하며 존재하지 않는 교육 링크를 만들지 않는다

### Requirement: 교육 상세 정보
시스템은 `/educations/<slug>/`에서 교육명·한 줄 소개·대표 이미지·교육목표·추천대상·시수별 커리큘럼을 제공해야 한다(SHALL). 커리큘럼은 과정 길이별 교시 순서를 보존해야 한다(SHALL). 원문 링크·수집일·편집 설명 등 프리셋 수집 기록은 상세 화면에 표시하지 않아야 한다(SHALL).

#### Scenario: 등록 교육 조회
- **WHEN** 익명 방문자가 존재하는 교육의 상세 URL에 접근한다
- **THEN** HTTP 200으로 해당 교육의 정보와 모든 시수 구성의 커리큘럼을 표시하고 수집 기록 영역 없이 랜딩으로 돌아갈 수 있다

#### Scenario: 없는 교육 조회
- **WHEN** 등록되지 않은 slug로 상세 URL에 접근한다
- **THEN** HTTP 404를 반환한다

### Requirement: 반응형 레이아웃과 접근 가능한 탐색
시스템은 모바일·태블릿·데스크톱에서 핵심 교육 정보와 탐색 기능을 제공해야 한다(SHALL). 본문·이미지·커리큘럼은 잘림이나 페이지 전체의 가로 스크롤 없이 읽을 수 있어야 하며, 링크는 키보드와 터치로 사용할 수 있어야 한다(SHALL).

#### Scenario: 화면 너비에 따른 배치
- **WHEN** 360px·768px·1280px 너비에서 랜딩과 교육 상세를 확인한다
- **THEN** 모바일 카드가 1열로 배치되고 넓은 화면에는 카드가 다열로 배치되며 본문과 커리큘럼이 겹치거나 잘리지 않는다

#### Scenario: 키보드와 이미지 설명
- **WHEN** 키보드로 주요 링크를 탐색하거나 이미지의 대체 텍스트를 확인한다
- **THEN** 포커스를 식별하고 상세·랜딩 사이를 이동할 수 있으며 정보성 이미지에 교육 내용을 설명하는 대체 텍스트가 제공된다

### Requirement: 환경에 맞는 이미지와 자산 제공
시스템은 개발 모드에서 로컬 미디어, 운영 모드에서 S3에 저장된 이미지를 CloudFront HTTPS URL로 제공해야 한다(SHALL). 동일한 교육 데이터는 도메인에 종속되지 않아야 하며 실행 시 교육 원본 사이트 요청이나 프론트엔드 빌드를 요구하지 않아야 한다(SHALL).

#### Scenario: 외부 연결 없는 화면 확인
- **WHEN** 개발 의존성 설치·DB 준비·초기 데이터 설정이 완료된 checkout에서 dev 모드로 외부 연결 없이 Django를 실행한다
- **THEN** 두 페이지의 CSS·이미지·필수 글꼴이 로컬 자산으로 정상 표시된다

#### Scenario: 운영 이미지 URL 제공
- **WHEN** 운영 settings와 S3·CloudFront 설정을 선택하고 대상 저장소에 이미지가 준비된 교육 페이지를 조회한다
- **THEN** 이미지 링크는 지정한 CloudFront의 HTTPS URL을 사용하며 DB에는 저장소 상대 이름만 존재하고 개발용 미디어 서빙 URL은 등록되지 않는다

### Requirement: 명시적인 개발·운영 설정 선택
시스템은 개발·운영 설정을 명시적으로 선택할 수 있어야 하며 기존 프로세스의 설정 모듈 지정을 보존해야 한다(SHALL). 기본 로컬 실행은 개발 설정을 사용하고 AWS 자격 증명이나 연결을 요구하지 않아야 한다(SHALL). 운영 설정 오류는 로컬 fallback 없이 보고해야 한다(SHALL).

#### Scenario: 로컬 기본 실행
- **WHEN** 설정 모듈을 지정하지 않고 개발 명령을 실행한다
- **THEN** 개발 설정과 로컬 미디어를 사용하며 AWS 백엔드를 초기화하거나 자격 증명을 조회하지 않는다

#### Scenario: 운영 설정의 누락 또는 충돌
- **WHEN** 운영 설정에서 버킷·리전·CloudFront 도메인·허용 host가 누락되거나 DEBUG 활성화를 요청한다
- **THEN** 민감값을 노출하지 않는 설정 오류로 중단하고 개발 설정이나 로컬 저장소로 전환하지 않는다

### Requirement: 개발·운영 의존성 설치 분리
프로젝트는 기본 개발 설치에 공통 실행 패키지와 개발·운영 추가 패키지를 포함하고 운영 설치에는 공통 실행 패키지와 운영 추가 패키지만 포함해야 한다(SHALL). 설치 프로필은 dev·prod만 제공하며 설정 로딩 중 패키지를 설치하거나 제거하지 않아야 한다(SHALL).

#### Scenario: 최소 운영 환경 구성
- **WHEN** 문서의 운영 설치·실행 절차로 새 환경을 구성한다
- **THEN** S3 저장소 의존성은 설치되고 Ruff 등 개발 도구는 설치되지 않으며 실행 시 개발 도구가 다시 설치되지 않는다

#### Scenario: 전체 개발 환경 구성
- **WHEN** 문서의 기본 개발 설치 절차로 새 환경을 구성한다
- **THEN** 공통 실행 패키지·개발 도구·운영 연동 패키지를 사용할 수 있고 기본 실행은 로컬 저장소를 사용한다

### Requirement: 교육 운영 정보와 상담 접수 상태
시스템은 교육별 코치 출강 또는 코스웨어 운영 방식, 선택적인 일반 텍스트 진행 안내, 상담 접수 활성 여부를 저장해야 한다(SHALL). 수집 기록은 운영 모델에 저장하지 않아야 한다(SHALL). migration 이력 정리는 사용자 승인으로 초기화한 빈 개발 DB를 대상으로 해야 한다(SHALL).

#### Scenario: 운영 정보 저장과 조회
- **WHEN** 유효한 운영 방식·진행 안내·접수 활성 여부를 가진 교육을 저장하고 다시 조회한다
- **THEN** 각 값이 보존되고 코스웨어와 코치 출강을 구분할 수 있다

#### Scenario: 빈 개발 DB의 전환
- **WHEN** 사용자 승인으로 초기화한 빈 개발 DB에 0001과 Django가 생성한 단일 0002를 적용한다
- **THEN** 수집 기록 열 없이 운영 정보와 UUIDv7 필드를 가진 교육 테이블을 생성하고 프리셋을 설정할 수 있다

### Requirement: 교육 콘텐츠의 재사용 가능한 입력 검증
교육 입력 검증은 비어 있지 않은 문자열 목록인 목표·추천대상과 기존 시수별 커리큘럼 구조를 검사해야 한다(SHALL). 시수는 중복 없는 양의 정수이고 교시 수와 일치하며 교시는 1부터 순서대로 주제·활동·설명을 가져야 한다(SHALL). 잘못된 운영 방식과 콘텐츠는 해당 필드의 검증 오류로 보고해야 한다(SHALL).

#### Scenario: 정상 콘텐츠 검증
- **WHEN** 등록된 두 운영 방식 각각에 대해 기존 프리셋 형태의 콘텐츠와 선택적인 빈 진행 안내를 입력 검증한다
- **THEN** 정상으로 처리되고 콘텐츠와 운영 방식이 임의로 변환되지 않는다

#### Scenario: 잘못된 콘텐츠의 오류 식별
- **WHEN** 목표·추천대상이 빈 목록 또는 공백·문자열 외 항목을 포함하거나 커리큘럼에 잘못된 구조·중복 시수·boolean 시수·교시 수 불일치·교시 순서 오류·필수 설명 누락이 있다
- **THEN** 해당 필드의 검증 오류가 반환되고 구조 접근 중의 예외가 그대로 노출되지 않는다

#### Scenario: 정의되지 않은 운영 방식
- **WHEN** 정의되지 않은 운영 방식으로 교육 입력을 검증한다
- **THEN** 운영 방식 필드의 검증 오류를 보고한다

### Requirement: 공개 교육 운영 안내

공개 상세는 운영 방식과 상담 접수 가능·중단 상태를 제공하고, 진행 안내가 있으면 일반 텍스트로 표시해야 한다(SHALL). 접수 중단은 소개 공개를 중단하지 않아야 하며, 상담 접수를 수강·일정 확정으로 안내하지 않아야 한다(SHALL). 접수 가능한 교육에는 실제 신청 페이지 링크를 제공하고 중단 교육에는 신청 진입을 비활성화해야 한다(SHALL).

#### Scenario: 접수를 중단한 교육 소개
- **WHEN** 상담 접수가 비활성인 교육의 랜딩과 상세를 익명으로 조회한다
- **THEN** 기존 교육 탐색과 상세 정보는 유지되고 상세에는 상담 접수 중단 상태가 표시되며 신청 링크는 활성화되지 않는다

#### Scenario: 운영 안내의 표시와 escaping
- **WHEN** 진행 안내에 HTML 형태의 문자열이 있는 교육 상세를 조회한다
- **THEN** 운영 방식·접수 상태와 함께 안내가 HTML 실행 없이 텍스트로 표시된다

#### Scenario: 진행 안내가 없는 교육
- **WHEN** 진행 안내가 빈 교육 상세를 조회한다
- **THEN** 빈 안내 영역 없이 운영 방식과 접수 상태를 확인할 수 있고 접수 가능한 경우 실제 신청 페이지로 이동할 수 있다

### Requirement: 교육별 이미지 저장과 기존 참조 호환
새로 저장하는 교육 이미지는 교육별 고정 UUIDv7 media_id의 32자 hex 하위 경로로 분리해야 한다(SHALL). media_id는 DB 저장 전에 생성되고 고유하며 편집 입력에서 제외되어야 한다(SHALL). slug 수정과 이미지 교체는 media_id를 변경하지 않아야 한다(SHALL). 일반 파일 저장은 원본 파일명 대신 UUID 파일명을 사용하고 기존 파일을 덮어쓰지 않으며 저장소가 반환한 실제 키를 참조해야 한다(SHALL). 기존 경로의 파일·참조는 자동으로 이동하거나 변경하지 않아야 한다(SHALL).

#### Scenario: 같은 이름의 파일 저장
- **WHEN** 같은 원본 파일명을 가진 서로 다른 이미지를 교육에 저장한다
- **THEN** 교육별 경로 아래 서로 다른 UUID 파일명이 사용되고 이전 파일 내용은 덮어쓰이지 않는다

#### Scenario: 저장소가 파일명을 조정한 경우
- **WHEN** 저장소가 요청한 이름과 다른 이름으로 파일을 저장한다
- **THEN** 교육은 저장소가 반환한 실제 이름으로 파일을 조회한다

#### Scenario: 저장 전 식별자와 slug 변경 후 이미지 교체
- **WHEN** 아직 DB에 저장하지 않은 교육의 이미지 경로를 생성하거나 기존 교육의 slug 변경 후 새 이미지를 저장한다
- **THEN** 저장 전에도 UUIDv7 폴더가 결정되고 slug 변경 전후 같은 media_id 폴더를 사용한다

#### Scenario: 기존 경로와 slug 변경
- **WHEN** 기존 경로의 이미지를 참조하는 교육을 조회하거나 이미지 교체 없이 slug만 수정한다
- **THEN** 기존 파일 키가 유지되고 이미지가 정상 제공되며 파일 이동이나 복제가 발생하지 않는다

### Requirement: 교육 삭제 후 미참조 이미지 정리

단일 또는 일괄 교육 삭제와 연결 이미지 정리 작업은 함께 영속화되어야 하며 commit 이후 비동기 작업에서 다른 교육 참조를 재확인하고 미참조 파일만 해당 저장소에서 정리해야 한다(SHALL). rollback되거나 다른 교육이 참조하는 파일은 보존해야 한다(SHALL). 이 계약은 기존 경로와 새 경로 모두에 적용해야 한다(SHALL).

#### Scenario: 단일 또는 일괄 삭제의 commit
- **WHEN** 이미지가 연결된 교육을 단일 또는 일괄 삭제하고 transaction이 commit된다
- **THEN** commit 전에는 파일과 다른 실행기에서 보이는 큐에 변화가 없고 commit 후 정리 작업이 실행되면 다른 교육이 참조하지 않는 연결 파일만 정리된다

#### Scenario: 삭제 rollback과 공유 참조
- **WHEN** 교육 삭제가 rollback되거나 작업 실행 시 다른 교육이 같은 파일을 참조한다
- **THEN** rollback 시 작업도 남지 않고 공유 파일은 유지되어 남아 있는 교육의 이미지 조회가 깨지지 않는다

#### Scenario: 교육 삭제 후 재연결
- **WHEN** 삭제 후 정리 작업 실행 전에 다른 교육이 같은 파일 키를 연결한다
- **THEN** 작업 실행 시 재연결을 확인해 파일을 보존한다

### Requirement: 이미지 교체 후 이전 파일 정리

모델 저장을 통한 이미지 교체와 이전 파일 정리 작업은 함께 영속화되고 commit 이후 비동기 작업에서 다른 교육이 참조하지 않는 이전 파일만 정리해야 한다(SHALL). 같은 파일 키를 유지하거나 이미지 필드를 저장하지 않는 수정은 파일을 삭제하지 않아야 한다(SHALL). 교체가 rollback되면 이전 파일을 보존해야 한다(SHALL).

#### Scenario: 이미지 교체와 rollback
- **WHEN** 새로운 이미지로 교체하고 transaction을 commit하거나 rollback한다
- **THEN** commit 후 정리 작업에서 현재 이미지와 공유 참조는 유지하고 미참조 이전 파일만 정리하며 rollback 시 이전 파일과 참조를 유지하고 정리 작업은 남기지 않는다

#### Scenario: 이미지와 무관한 수정
- **WHEN** 이미지 키를 그대로 두거나 이미지 필드를 제외한 저장으로 교육의 소개·운영 정보만 수정한다
- **THEN** 연결 이미지와 저장소 파일이 변경되거나 삭제되지 않는다

#### Scenario: 대기 중 이전 이미지로 복귀
- **WHEN** 이미지 교체 후 작업 실행 전에 원래 이미지 키로 다시 연결한다
- **THEN** 각 작업이 실행 시점의 참조를 확인해 현재 연결 파일을 보존하고 미참조 교체 파일만 정리한다

### Requirement: 파일 정리 실패의 식별

commit 이후 파일 정리 실패는 credential·민감한 예외 본문 노출 없이 대상 키와 오류 종류로 식별하고 총 3회 시도 후 실패 목록에 보존해야 한다(SHALL). 이미 commit된 교육 삭제·교체를 rollback한 것으로 보고하지 않아야 한다(SHALL). 저장 실패·rollback으로 새 파일이 남을 수 있으며 저장소 전체나 프리셋 원본을 청소하지 않아야 한다(SHALL).

#### Scenario: 저장소 삭제 실패
- **WHEN** DB commit 이후 파일 저장소가 삭제 오류를 반환한다
- **THEN** 삭제 실패와 시도가 기록되고 DB의 commit 결과는 유지되며 다른 연결 파일에 대한 무차별 삭제는 수행하지 않고 한도 초과 시 자동 시도를 멈춘다

#### Scenario: 실패 작업 재등록과 없는 파일
- **WHEN** 실패 작업을 재등록하거나 이미 삭제된 파일의 작업이 다시 실행된다
- **THEN** 현재 참조를 재검사하고 미참조인 대상만 삭제하며 없는 파일은 성공으로 처리하고 프리셋 원본은 건드리지 않는다

#### Scenario: 큐 기록 저장 실패
- **WHEN** 이미지 변경 또는 교육 삭제의 정리 작업을 영속 등록할 수 없다
- **THEN** 해당 DB 변경도 rollback되어 정리 대상 키가 사라진 채 성공 처리되지 않는다
