# education-presets Specification

## Purpose

평가자가 별도 콘텐츠 입력이나 원본 사이트 접근 없이 히어로스쿨 교육 3개로 초기 환경을 재현할 수 있게 한다. 초기 설정을 반복해도 기존 교육 데이터를 보존하며, 제공 데이터의 출처와 수집 시점을 확인할 수 있도록 한다.

## Requirements

### Requirement: 고정 교육 프리셋 제공
프로젝트는 프롬프트 히어로·감정탐험 히어로·관계 히어로의 교육명·한 줄 소개·이미지·목표·추천대상·시수별 커리큘럼을 포함하는 고정 프리셋을 제공해야 한다(SHALL). 원문 URL과 실제 수집일을 함께 기록하고, 요약·편집한 내용은 원문과 구별해야 한다(SHALL).

#### Scenario: 프리셋 내용 확인
- **WHEN** 평가자가 제공된 프리셋과 출처 기록을 확인한다
- **THEN** 정확히 지정된 교육 3개와 각 교육의 필수 소개 데이터·로컬 이미지·원문 URL·수집일을 확인할 수 있다

### Requirement: 명령 하나로 초기 교육 설정
시스템은 migration을 완료한 빈 DB에 명령 하나로 교육 3개와 이미지를 선택된 미디어 저장소에 저장하고 결과를 보고해야 한다(SHALL). 개발 모드에서는 원본 사이트·외부 API·AWS 자격 증명을 요구하지 않아야 한다(SHALL). 운영 모드에서는 준비된 S3에 명시적으로 저장해야 한다(SHALL).

#### Scenario: 새 평가 환경 초기화
- **WHEN** 평가자가 README의 개발 절차로 migration 후 초기 데이터 명령을 실행한다
- **THEN** 교육 3개가 영속 저장되고 이미지는 로컬 미디어에 복사되어 랜딩과 상세에서 조회되며 생성 건수가 출력된다

#### Scenario: 운영 저장소 초기화
- **WHEN** 운영 모드를 선택하고 준비된 S3에 초기 데이터 명령을 명시적으로 실행한다
- **THEN** 필요한 이미지가 해당 저장소에 저장되고 교육의 이미지 URL은 CloudFront를 사용하며 AWS 리소스는 자동 생성하지 않는다

### Requirement: 반복 설정 시 기존 데이터 보존
시스템은 초기 데이터 명령 재실행 시 이미 존재하는 교육과 연결 이미지를 덮어쓰거나 중복 생성하지 않아야 한다(SHALL). 프리셋 외의 기존 교육·파일·객체도 변경하거나 삭제하지 않아야 한다(SHALL).

#### Scenario: 수정된 교육을 보존하는 재실행
- **WHEN** 초기화한 교육의 소개를 변경하고 별도 교육을 추가한 후 명령을 다시 실행한다
- **THEN** 수정 내용·이미지 참조·이미지 파일과 별도 교육은 그대로 유지되고 프리셋 교육이 중복되지 않으며 생성·건너뛴 건수가 보고된다

#### Scenario: 일부 교육만 존재하는 환경
- **WHEN** 지정된 교육 중 일부만 존재하는 DB에서 명령을 실행한다
- **THEN** 없는 교육과 필요한 이미지만 추가되고 기존 교육·이미지는 유지된다

### Requirement: 잘못된 프리셋의 부분 저장 방지
시스템은 프리셋의 필수 데이터와 참조 이미지 원본을 쓰기 전에 검증해야 한다(SHALL). 입력·저장소·DB 오류는 원인을 식별할 수 있게 보고하고 해당 실행의 교육 데이터를 부분 저장하지 않아야 한다(SHALL). DB 롤백 후 파일이 남는 경우 이를 보고하고 기존 객체를 자동 삭제하지 않아야 한다(SHALL).

#### Scenario: 필수 정보 또는 로컬 이미지 누락
- **WHEN** 프리셋에 필수 소개 정보나 참조 이미지가 누락된 상태에서 초기 데이터 명령을 실행한다
- **THEN** 쓰기 전에 실패를 보고하고 해당 실행으로 교육이나 이미지를 저장하지 않는다

#### Scenario: 이미지 저장 도중 실패
- **WHEN** 일부 이미지 저장 후 저장소 오류 또는 DB 오류가 발생한다
- **THEN** 실패를 보고하고 해당 실행의 DB 변경을 롤백하며 이미 저장되어 남을 수 있는 파일을 알리고 기존 파일·객체를 자동 삭제하지 않는다

#### Scenario: 실패 후 다시 초기화
- **WHEN** 앞선 실패로 프리셋 전용 이미지가 저장소에 남은 상태에서 명령을 다시 실행한다
- **THEN** 같은 원본의 기존 이미지를 재사용해 교육을 설정하고 불필요한 파일 복제나 기존 이미지 덮어쓰기를 하지 않는다

### Requirement: 초기 교육의 운영 정보
고정 교육 3개의 프리셋은 코치 출강 운영 방식·일정과 진행 조건을 상담 후 협의한다는 안내·상담 접수 활성 여부를 명시해야 한다(SHALL). 안내는 과제의 접수 정책임을 편집 설명으로 구별하고 확인되지 않은 원본의 가격·정원·지역·모집기간을 확정 정보로 제공하지 않아야 한다(SHALL).

#### Scenario: 빈 DB의 운영 정보 설정
- **WHEN** migration 후 초기 데이터 명령으로 빈 DB를 설정한다
- **THEN** 기존 교육 3개와 이미지가 생성되고 각 교육의 운영 방식·진행 안내·상담 접수 상태가 프리셋과 일치한다

#### Scenario: 편집한 운영 정보의 재실행 보존
- **WHEN** 기존 교육의 운영 방식·진행 안내·상담 접수 상태를 수정한 후 초기 데이터 명령을 다시 실행한다
- **THEN** 수정한 값과 기존 콘텐츠·이미지가 유지되고 중복 교육이 생성되지 않는다

### Requirement: 초기 데이터와 교육 입력 검증의 일치
초기 데이터 명령은 교육 입력과 동일한 운영 방식·목표·추천대상·커리큘럼 검증 계약을 사용해야 한다(SHALL). 프리셋 전체의 콘텐츠 또는 이미지 입력에 오류가 있으면 기존 부분 저장 방지 계약에 따라 DB와 저장소 쓰기를 시작하지 않아야 한다(SHALL).

#### Scenario: 운영 방식 또는 콘텐츠가 잘못된 프리셋
- **WHEN** 프리셋에 정의되지 않은 운영 방식이나 교육 입력 검증에서 거부하는 목표·추천대상·커리큘럼이 있다
- **THEN** 초기화 실패를 식별 가능한 오류로 보고하며 해당 실행으로 교육과 이미지를 생성하지 않는다

#### Scenario: 공통 검증으로 전환한 뒤 저장 실패
- **WHEN** 유효한 프리셋을 저장하는 과정에서 저장소 또는 DB 오류가 발생한다
- **THEN** 기존 DB 롤백·잔여 파일 안내·재실행 시 파일 재사용 계약이 유지된다

### Requirement: 교육별 프리셋 이미지 경로와 재사용
신규 프리셋 이미지 파일은 프리셋에 기록한 교육별 고정 UUIDv7의 32자 hex images 하위 경로와 원본 내용의 SHA256 파일명을 사용해야 한다(SHALL). 기존 교육의 이미지 키는 변경하지 않으며, 초기화 재실행과 실패 후 재실행에서는 같은 원본의 새 규칙 경로에 남은 파일을 재사용해야 한다(SHALL). 저장소가 이름을 조정하면 반환된 이름을 참조해야 한다(SHALL). media_id의 누락·잘못된 형식·UUIDv7이 아닌 값·프리셋 내 중복은 DB·파일 쓰기 전에 거부해야 한다(SHALL).

#### Scenario: 신규 교육의 이미지 저장
- **WHEN** 빈 DB와 저장소에 교육 3개를 초기화한다
- **THEN** 이미지가 각 교육의 images 하위 경로에 SHA256 기반 PNG 파일명으로 저장되고 실제 저장 키가 교육에 연결된다

#### Scenario: 기존 교육과 이미지의 보존
- **WHEN** 기존 형식 경로의 이미지를 참조하는 교육이 있는 상태에서 초기화 명령을 실행한다
- **THEN** 해당 교육의 이미지 키·파일·운영 정보는 보존되고 없는 교육에 필요한 이미지 저장만 새 경로 규칙을 사용한다

#### Scenario: 실패 잔여 파일의 재사용과 재생성
- **WHEN** 앞선 실패로 새 규칙 경로의 이미지가 남아 있거나, 교육 삭제 후 파일 정리가 끝난 상태에서 초기화를 재실행한다
- **THEN** 남아 있는 같은 원본 파일은 재사용하고 정리되어 없는 파일은 다시 생성하며 기존 연결 파일을 덮어쓰지 않는다

### Requirement: 수집 기록과 운영 필드의 분리
source_url·source_image_url·collected_on·editorial_note는 프리셋 JSON에만 보관하고 Education 모델에 저장하지 않아야 한다(SHALL). 초기화는 이 값을 모델 생성 인자에서 제외해야 한다(SHALL).

#### Scenario: 수집 기록이 포함된 프리셋 초기화
- **WHEN** 수집 기록과 교육 운영 필드가 함께 있는 JSON으로 초기화한다
- **THEN** 교육 3개와 이미지는 정상 생성되고 수집 기록은 JSON에 남으며 DB 열에는 존재하지 않는다

### Requirement: 선택적 교육신청 샘플 준비

초기 데이터 명령은 `--with-applications`를 명시한 경우에만 교육신청 샘플 32건을 준비해야 한다(SHALL). 옵션이 없으면 신청·상담·메일 샘플을 만들지 않고 기존 교육·이미지 준비와 운영 저장소 초기화 계약을 유지해야 한다(SHALL). 결과에는 교육과 신청 각각의 생성·건너뜀 건수를 구분해야 한다(SHALL).

#### Scenario: 기존 기본 명령 실행
- **WHEN** 신청 옵션 없이 교육 초기 데이터 명령을 실행한다
- **THEN** 없는 교육과 필요한 이미지만 준비하며 신청·상담·메일·계정을 추가하지 않고 기존 운영 저장소 동작도 유지한다

#### Scenario: 빈 신청 환경에서 선택 생성
- **WHEN** 유효한 개발 환경과 기존 담당자를 지정하여 `seed_educations --with-applications --staff-user <사용자명>`을 실행한다
- **THEN** 교육 3개와 해당 교육에 연결된 신청 32건을 준비하고 교육·신청별 생성·건너뜀 건수를 보고한다

### Requirement: 백오피스 확인용 신청 배분과 혼합 순서

샘플은 프롬프트 히어로·감정탐험 히어로·관계 히어로에 각각 11·11·10건을 배분하고 접수 8·상담중 6·재연락 10·완료 4·취소 4건을 포함해야 한다(SHALL). 최초 생성 후 최신순의 두 페이지 모두 세 교육과 다섯 신청 상태를 포함해야 한다(SHALL). 샘플만 있는 환경에서 첫 페이지는 20건, 두 번째는 12건이어야 한다(SHALL).

#### Scenario: 전체 목록과 조건 유지
- **WHEN** 샘플만 있는 환경에서 최신순 목록의 첫 페이지와 두 번째 페이지를 연다
- **THEN** 20·12건이 중복이나 누락 없이 표시되고 두 페이지 모두 교육·상태가 섞여 있으며 검색·교육·상태·재연락 조건은 페이지 링크에 보존된다

#### Scenario: 샘플 검색과 기존 신청 공존
- **WHEN** 일반 신청이 있는 환경에 샘플을 추가하고 샘플 전용 이메일 접두어로 검색한다
- **THEN** 검색 결과에서 샘플 32건과 20·12건 분할을 확인할 수 있고 일반 신청은 변경되지 않으며 전체 목록 건수는 기존 신청을 포함한다

### Requirement: 한국 시각 기준의 최초 날짜 구성

날짜는 실행에서 한 번 확보한 현재 시각과 한국 날짜를 기준으로 최초 생성할 때 계산해야 한다(SHALL). 접수는 현재부터 과거로 분산하고 미래 접수를 만들지 않아야 한다(SHALL). 연락 가능 날짜는 접수의 한국 날짜보다 앞서지 않으면서 과거·오늘·미래 사례를 포함해야 한다(SHALL). 상담은 해당 접수 이후부터 기준 현재 시각 사이에 있어야 한다(SHALL).

#### Scenario: 한국 자정과 UTC 날짜 차이
- **WHEN** 한국 날짜와 UTC 날짜가 다른 시점 또는 한국 자정 직후에 샘플을 생성한다
- **THEN** 오늘 사례가 한국 날짜와 일치하고 미래 접수나 접수 이전 연락 날짜·상담이 없으며 모든 저장 시각은 시간대가 있는 값이다

#### Scenario: 나중 날짜에 재실행
- **WHEN** 생성 다음 날 이후에 같은 옵션으로 다시 실행한다
- **THEN** 기존 샘플의 접수·연락·재연락·상담·메일 시각을 현재 기준으로 다시 이동시키지 않는다

### Requirement: 재연락과 종료 사례 구성

최초 샘플의 재연락 10건은 한국 날짜 기준 오늘 3·이전 날짜 3·이후 날짜 2·일정 미정 2건으로 구성해야 한다(SHALL). 재연락 외 상태의 현재 일정은 비우고 취소 4건에는 가상 취소 사유를 포함해야 한다(SHALL). 오늘 중 지난 일정이 기한 경과에도 포함되는 기존 필터 의미는 유지해야 한다(SHALL).

#### Scenario: 오늘과 기한 경과의 겹침
- **WHEN** 생성일에 오늘·기한 경과·일정 미정 필터를 확인한다
- **THEN** 오늘은 3건, 일정 미정은 2건이며 기한 경과는 이전 날짜 3건에 오늘 중 현재보다 이른 일정을 더한 결과다

#### Scenario: 완료와 취소 상세
- **WHEN** 완료·취소 샘플을 확인한다
- **THEN** 현재 다음 연락 예정은 없고 취소에는 사유가 있으며 남은 상담·안내 증거는 해당 종료 상태와 모순되지 않는다

### Requirement: 가상 개인정보와 기존 담당자의 상담 사례

이름·주소·상담 내용은 가상 데이터이고 이메일은 `example.com`이어야 한다(SHALL). 상담 없음·복수 상담·부재중·재연락 합의·같은 신청 원기록에 대한 정정을 포함해야 한다(SHALL). 상담 작성자는 명시한 기존 활성 staff로 기록하고 계정 생성·권한 변경·기본 비밀번호 설정을 하지 않아야 한다(SHALL). 샘플임을 데이터와 안내에서 식별할 수 있어야 한다(SHALL).

#### Scenario: 담당자 누락 또는 부적합
- **WHEN** 신청 옵션에 담당자가 없거나 존재하지 않는 사용자·비활성 사용자·staff가 아닌 사용자를 지정한다
- **THEN** DB·이미지 쓰기 전에 오류로 중단하고 계정을 자동 선택하거나 생성·변경하지 않는다

#### Scenario: 상담과 정정 확인
- **WHEN** 지정한 기존 담당자로 생성한 대표 상세에서 상담들을 확인한다
- **THEN** 상담 작성자·시각·내용·당시 일정과 정정 대상이 일관되고 정정 전 원문이 보존되며 모든 내용이 가상 사례임을 알 수 있다

### Requirement: 개발 모의 메일 상태와 외부 효과 제한

신청 샘플 옵션은 개발 설정·모의 전송 모드·외부 전송 없는 locmem backend에서만 허용하고 나머지는 쓰기 전에 거부해야 한다(SHALL). 샘플 생성은 메일 발송·큐/스케줄 등록·공유 전송 예산 생성을 하지 않아야 한다(SHALL). 안내는 pending·queued·sending·simulated·retry_wait·failed·unknown·suppressed를 포함하되 합성 accepted·SES 접수 시각·SES MessageId는 만들지 않아야 한다(SHALL).

#### Scenario: 운영 또는 외부 전송 backend
- **WHEN** 운영 설정 또는 SES 모드 또는 외부 전송 가능한 메일 backend에서 신청 옵션을 실행한다
- **THEN** 교육·이미지를 포함한 쓰기를 시작하기 전에 명확한 오류로 중단하고 옵션 없는 운영 교육 초기화는 계속 지원한다

#### Scenario: 합성 처리 기록 확인
- **WHEN** worker를 중지한 상태로 최초 샘플을 생성하고 안내·전송 시도와 큐를 확인한다
- **THEN** 실제 발송과 큐/스케줄 등록이 없고 상태별 시각·시도 횟수·현재 시도 연결이 일치하며 SES 증거는 비어 있고 안내·문구에서 화면 확인용 합성 상태임을 알 수 있다

#### Scenario: worker를 시작한 이후
- **WHEN** 초기 화면 확인을 마친 뒤 개발 worker와 안내 검사를 실행한다
- **THEN** 도래한 대기·재시도 대상과 만료된 큐·발송 중 대상은 기존 처리·복구 정책에 따라 변할 수 있고 재실행으로 초기 샘플 상태를 복구하지 않으며 실제 외부 전송은 없다

### Requirement: 샘플 식별과 수정 보존

샘플마다 고정된 제출 식별자를 사용하고 기존 식별자가 있으면 해당 신청과 상담·안내·전송 시도·이력을 덮어쓰거나 추가하지 않아야 한다(SHALL). 원본 식별 정보가 샘플과 충돌하면 기존 데이터를 변경하지 않고 실패해야 한다(SHALL). 누락 샘플만 추가하고 일반 신청·계정·기존 교육·미디어를 삭제하거나 초기화하지 않아야 한다(SHALL).

#### Scenario: 담당자가 변경한 샘플 재실행
- **WHEN** 담당자가 샘플의 개인정보·상태·일정 변경과 상담 추가를 한 뒤 다른 날 다시 명령을 실행한다
- **THEN** 원본과 수정값·상담·안내·전송 시도·이력·날짜가 그대로 유지되고 중복 생성이나 이력 추가가 없다

#### Scenario: 일부 샘플만 있는 환경
- **WHEN** 고정 식별자 중 일부만 존재하는 환경에서 실행한다
- **THEN** 없는 신청과 그 종속 기록만 현재 실행 기준으로 함께 추가하며 존재하는 신청의 누락 종속 기록을 자동 복구하거나 수정하지 않는다

#### Scenario: 식별자 충돌
- **WHEN** 고정 식별자에 연결된 불변 최초 제출의 샘플 이메일·교육 식별 정보가 예상과 다르다
- **THEN** 기존 데이터를 덮어쓰거나 일반 신청을 샘플로 편입하지 않고 충돌을 보고하며 해당 실행의 DB 변경을 취소한다

### Requirement: 신청 샘플 실행의 부분 저장 방지

전체 입력·환경·담당자와 신규 샘플의 관계를 검증하고 교육·신청·상담·안내·전송 시도·이력의 해당 실행 DB 변경을 모두 성공하거나 모두 롤백해야 한다(SHALL). 파일 쓰기는 기존 잔여 파일 안내·재사용 계약을 유지해야 한다(SHALL). 성공한 DB commit 후에만 생성 결과를 보고하고 실패 로그에는 개인정보·비밀값을 노출하지 않아야 한다(SHALL).

#### Scenario: 잘못된 상담 또는 메일 관계
- **WHEN** 입력에 접수 전 상담·다른 신청의 정정 대상·시도 횟수와 시도 기록의 불일치가 있다
- **THEN** 성공으로 처리하지 않고 해당 실행의 DB 변경을 남기지 않는다

#### Scenario: 중간 저장 또는 이력 기록 실패
- **WHEN** 일부 신청 저장 후 상담·안내·전송 시도·이력·DB 저장에서 오류가 발생한다
- **THEN** 해당 실행에서 추가한 교육을 포함해 DB 변경 전체가 취소되고 기존 데이터는 유지되며 저장소 파일이 남을 수 있으면 이를 알리고 자동 삭제하지 않는다
